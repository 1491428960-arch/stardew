### ⚠ 关于「权威源」——这里曾经有两种说法

`docs/README.md` 早期版本写「当前值的唯一权威源是 `.dsh/memory/current-state.md`」。
实际情况是**两条工作线各自维护一份状态**，**不是一个项目的总状态**：

| 状态文件 | 覆盖哪条线 | 最后更新 |
|---|---|---|
| `STATE.md` | **prompt 指令 / 约束 / 长度**这条线 | 2026-09-28 |
| `.dsh/memory/current-state.md` | **语言指纹管线**那条线 | 2026-09-26 |

且 `current-state.md` 自己的头部就写着「**本文件只是指针，不是状态本体**」，
但它有 38 KB 正文 —— 读的时候注意这个自相矛盾。

**⇒ 现在只认一条规则：想知道「项目现在什么状态、下一步干什么」，读 `STATE.md`。**

## 目录结构约定

| 前缀 | 含义 | 是否要维护 |
|---|---|---|
| `STATE.md` | **入口**：当前状态、已成立结论、否决清单、陷阱清单、改动清单 | **每次工作都要更新** |
| `active-work.md` | 权威工作日志，逐项带测试证据 | **每次工作都要追加**（写在**文件末尾**） |
| `constraint-scope.md` | 「指令冲突」线的台账与判定规则 | 台账变化时更新 |
| `report-*.md` | 研究报告 / 一次性结论 | 历史记录，**不再更新**（要改就写新报告） |
| `handoff-*.md` | 交接文档（给下一个会话／另一个人） | 状态变化时更新，作废的在头部标注 |
| `next-steps-*.md` | 待办清单（A 需拍板／B 可直接做／C 已判定不做） | 状态变化时更新 |
| `diagnosis-*.md` | 问题诊断记录 | 一次性，留档 |
| `design-*.md` | 交互与体验设计稿 | 历史记录，不再更新 |
| `deploy-*.md` / `checklist-*.md` | 部署与游戏内验证清单 | 流程变化时更新 |
| `plan-*.md` | 当日计划 | 当日产物，事后归档 |
| `manual-*.md` | 人工操作手册 | 流程变化时更新 |
| `npc-bubble-elements-*.md` / `.json` | 气泡元素规格（另一条工作线产出） | 由该线维护 |
| `test-cases.md` | 人工回归清单（游戏内步骤） | 环境变化时在顶部补提示 |
| `rebuild-index.md` | 资料索引重建手册 | 命令变化时更新 |

## 写文档的三条约定

1. **时间敏感的事实要带日期**——写「当前测试基线 N passed」时**必须同时给出取数日期**，
   否则几个月后会变成误导。
2. **不要在多处复制同一份状态**——状态写在一处，其他文档用**指针**指过去。
3. ⚠ **不要把更正补丁追加到归档报告里**。`report-*.md` 是「当时写成的事实」，
   后来的更正写在 `STATE.md` 或新报告里。混在一起会让读者分不清哪句是当时的判断、
   哪句是后来的修正。（2026-09-28 实际踩过：一处误判的更正一度被追加进归档报告。）
