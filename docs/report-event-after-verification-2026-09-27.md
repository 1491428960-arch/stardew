# 事件后晨间预设：真实生成验证（2026-09-27 晚）

## 一句话结论

29 条事件后预设抽 6 条做真实云端验证：**方向卡 18/18 全部认出**、`direction` / `boundaries`
/ `closingHook` 三层机制都在起作用。抓到 3 个问题 —— 其中 **1 个当场修掉并加了守卫**
（`closingHook` 的性别代词，54 条），另 1 个**取证后决定本轮不动代码**
（第三人称叙述体，是新形态），第 3 个归入写法口径。

## 一、为什么是这 6 条

29 条没法逐条验（每条 3 轮 ≈ 1.1 万 token）。沿用 fall / winter 抽样的口径：
**按「哪条 boundary 最容易失守」挑**。玩家台词是**照着 boundary 打的**，
不是随口问 —— 每句都往那条禁令上撞。

| 场景 | 撞的陷阱 |
|---|---|
| `event-after-abigail-spiritboard` | 追问她说破 / 被追问逼到缩回去 |
| `event-after-sebastian-rain` | 挑明「这儿能坐两个人」那层意思 |
| `event-after-alex-apology` | 把放弃职业队升华成悲剧 + 引出父亲 |
| `event-after-pierre-secret` | 逼问秘密 + 替 Caroline 表态 |
| `event-after-emily-dance` | 直接夸奖（她没在求夸）+ 玄学化 |
| `event-after-evelyn-cookies` | 复读她已交代过的保密句 |

## 二、方法

探针：`.tmp/event-after-verify/probe_event_after.py`（原始结果 `result.json`）。

每轮两件事：

1. `POST /api/context/preview` —— **零额度**，读 `morningScenarioId`，确认这段对话
   还认不认得出来。认人靠开场白逐字比对，**对失败是静默的**（少一层方向约束，
   回复照样生成），所以必须单独打出来。
2. `POST /api/dialogue/test` —— 真实云端生成。

3 轮是底线（1 轮只能看出「像不像」，看不出规则有没有在约束）。
history 首条是预设的 `opening`，之后逐轮追加。窗口按游戏端 `MaxHistoryItems = 6` 取最近条 ——
3 轮后 history 长度 7，**正好在第 4 轮才会把开场白挤出窗口**，所以 3 轮内方向卡都该在。

### ⚠ 开跑前必须先重载 Bridge

第一次跑**没有**先查端点：`morning.json` 是 163 条，而 `GET /api/morning/scenarios`
只返回 **144 条 / `event-after` 11 条** —— Bridge 停在「事件后只有 10 条」的旧版本上。
这是本项目反复记的那类失败（数据写对但永不生效）。**重载后端点 163 / 30，验证才成立。**

判据：**端点条数 != 文件条数 ⇒ 先重启 Bridge，别急着跑。**

### 3.3 三个发现

#### 发现一：第三人称叙述体 —— 新形态，Guard 覆盖不到（**本轮未改代码**）

`event-after-pierre-secret` 轮 2 的实际输出：

```
皮埃尔沉默了一瞬，手指在柜台边缘轻叩两下。

"家庭的事……不该从外人嘴里传出去。"他声音低下去，又很快抬眼，"种子新到了一批，南瓜和秋日野花，你要看看吗？"
```

**这是小说体，不是台词。** 游戏对话框里会直接出戏。

根因是**检测缺口**，不是提示词缺口：

- `guard.py:331` 的 `_stage_direction = re.compile(r"(?:（[^（）\r\n]{1,80}）|\([^()\r\n]{1,80}\))")`
  **只匹配括号内的动作旁白**；
- 而无括号的第三人称叙述（「他声音低下去」）**不在判据里**，于是整段放行；
- 重试提示词其实**已经覆盖**这种形态（「不要写动作、表情、手势、环境」），
  所以修的位置在**检测**，不在提示词。

**取证（零成本，扫 270 个历史工件）**：

| 语料 | 条数 | 含第三人称叙述动词 | 占比 |
|---|---:|---:|---:|
| `artifacts/character-quality-eval/*/results.jsonl` | 2481 | **0** | 0.0% |
| 本次 6 条 × 3 轮 | 18 | 1 | 5.6% |

> ⚠ 顺带否掉了一个看起来很像的判据：**中文引号不能当信号**。
> 历史里含引号的 38 条**全部是合法的「引用词」用法**
> （「别让"改天"这种词成了拖延的借口」「"第三组"目前的读数」），拦它会误伤这 38 条。

**假设（未验证）**：差异来自**方向卡**。`direction` 与 `closingHook` 都是**用第三人称描述角色**
（「他先探口风，因为在意体面」「我得去 + **他自己**手上的那件小事」），
模型可能把它当成了文风示范。这**不是**孤立现象 —— 本项目已经踩过两次同类坑：

1. Alex 那条 `closingHook` 里的例句被模型**原样当台词说了出去**（已记在
   `test_closing_hook_is_conditional_not_turn_counted` 的 docstring）；
2. spring 验证发现 `direction` 和 `boundaries` 打架时 **`direction` 赢**
   （模型蹦出「数据库连接池泄漏」）。

**为什么本轮不改 Guard**：证据只有 **1 条**，而要改的是**全链路共用的**格式守卫。
判据词表也不好定 —— 宽松了会误伤「我喊他停他就停了」这类正常台词，收窄了又不覆盖。
凭 1 个样本改共享机制，正是本项目反复警告的那类过度反应。

**下一步取证（明确、便宜）**：对 event 类多跑几批（每批 6 条 × 3 轮），
统计叙述体出现率；只有确认它稳定复现（比如 ≥3/24 轮），再按「角色名/代词 + 神态动词」
设计判据，并**先在 2481 条历史回复上跑一遍确认 0 误伤**。

#### 发现二：`closingHook` 的性别代词（**已修**）

163 条里 **154 条写「他自己」，只有 9 条写「她自己」**。而 `vanilla.json` 里
**36 个 persona 全都带 `pronouns`**（22 个 `he` / 14 个 `she`）。

14 个 `she` 角色共 63 条预设，**54 条用了「他自己」** —— 有人改过其中 5 个角色的部分条目
（9 条），没改完，于是 Abigail / Emily / Haley / Leah / Maru 身上**两种写法并存**。

这不是纯注释文案：`morning_scenario.py:488` 把 `closing_hook` 放进 `card["closing"]`，
**模型看得到**。

**修法**：判据取 persona 自己的 `pronouns`，**不另立性别名单**（名单会跟 persona 漂移）。
54 条一对一替换，涉及 Evelyn 5 / Leah 6 / Abigail 6 / Penny 5 / Emily 4 / Robin 4 /
Caroline 4 / Jodi 4 / Marnie 4 / Maru 3 / Sandy 3 / Haley 2 / Jas 2 / Pam 2。

**守卫**：新增 `test_closing_hook_matches_the_npc_pronoun`。
先写测试拿到红灯（54 条），修完转绿（97 passed）。守卫里加了一道**防空集**
（「用到的 npcId 必须都在 persona 表里」）—— 不在表里的角色会让比对悄悄跳过，
而漏过的表现和「全部通过」一模一样。

**格式安全**：改前先干跑「读→dump→比对」确认 `json.dumps(ensure_ascii=False, indent=2)`
与原文逐字一致（只差末尾换行），所以 diff 只落在那 54 行上，不是整文件重排。

#### 发现三：`emily-dance` 轮 1 兜底失败 + `closingHook` 被盖过

轮 1（玩家直接夸「你跳得真好」）拿到的是兜底文案：

```
（暂时没有合适的回复，请稍后再试。）
provider=fallback  warnings=['cloud provider failed', 'response_guard: format_stage_direction', 'fallback_guard: format_stage_direction']
```

链路是：模型输出了**括号动作** → 格式 Guard 判 `stage_direction` 要求重试 →
这次重试**云端失败** → 走兜底。**Guard 判对了**，失败在上游抖动（`cloud provider failed`
是本项目记录过的间歇故障，不是额度问题）。这一轮没有测到 boundary。

另外 `closingHook` 有一条约束**被角色特征盖过**：Emily 轮 3 在玩家问了一个真问题之后
**主动把话头交了回去**（「你呢，今天打算做点什么？」），而 `closingHook` 写的是
「只有当玩家这一轮只给了一句很短的应声……才把话头交回去」。她的 persona 就是
「热情开放、会主动多说」，`direction` 也写着「会主动多说」——**同一张卡里两股力气相反时，
persona 特征赢了**。这与 spring 那次「`direction` 赢过 `boundaries`」同型。

⇒ **口径记录**：`closingHook` 的「唯一一次交话头」是**软约束**，
角色特征强时会让位。**不要靠再加一条禁令去按住它**（真瓶颈不在这里）。

## 七、附：Guard 链路的代码考古（同日深夜）

§5.3 的 ③ 提出「`format_stage_direction` 触发后 6/6 都兜底」，并据此设想了一个
「方向卡口吻」的根因实验。**读代码把那个设想推翻了，也把兜底链路的真实机理弄清楚了。**

### 7.1 主假设被推翻：方向卡不是「小传口吻」

先把假设本身验了 —— 渲染一条真实的方向卡看它长什么样（`render_direction_card`）：

| 字段 | 实际口吻 |
|---|---|
| `instruction` | **对模型说话**（「顺着这条线聊下去，不要重新自我介绍」） |
| `direction` | **第三人称小传**（「她有点不好意思，但更多是开心有人知道了……她热情开放，会主动多说」） |
| `boundaries` | **对模型说话**（「不要说成「你跳得真好」这类评价」） |
| `closing` | **对模型说话**（「只有当玩家这一轮只给了一句很短的应声……你才把话头交回去」） |

4 个字段里**3 个本来就是指令口吻**，只有 `direction` 是第三人称。
⇒ 「整张卡是小传口吻、模型把它当文风示范」**不成立**，那个「改写成指令口吻做 A/B」的实验
**前提就错了，不该做**。

（`direction` 仍是唯一以叙述者视角描述角色状态的字段，值得继续留意，
但它单独撑不起一个 163 条的改写工程。）

**教训**：我连续两轮把「方向卡口吻」当根因在推，**却从没把卡片渲染出来看一眼**。
假设再自洽，也要先把它渲染出来、再设计实验。

### 7.2 重试机制比想象的健康

- 重试循环最多 5 轮（`guard.py:1229`），format 类**允许重试 2 次**（`guard.py:1349`）
- 第二条 format 重试会换更强的提示词（`FORMAT_RETRY_FINAL_CONTENT`：
  「不要写动作、表情、手势、环境或括号内容」）；第一条也明确写着
  「即使上一条包含括号，也绝不输出括号内容」
- 有一条旁路会把重试提示词换成弱版（`_NATURAL_RETRY_CONTENT["format"]`，
  **里面没有一句禁止括号**）—— 但 `prompts.py:6636` 注明**线上 `naturalMode` 恒 false**，
  且 `DialogueTestRequest` 是 `extra="forbid"`、这个开关根本传不进去，
  所以**这两批 36 轮走的都是强提示词**，该旁路与本次现象无关

⇒ 「重试机制坏掉」的猜想**排除**。

### 7.3 那 6/6 兜底到底是什么

`app.py:744-770` 的兜底链路是：主回复过 Guard → 不过就调 fallback provider →
**fallback 的回复也要过 Guard** → 再不过才用 `_SAFE_FALLBACK_REPLY`。

探针里看到的 `fallback_guard: format_stage_direction`，说明被拒的是 **fallback 那一层**的回复，
而它的形态正是**括号包裹的「（暂时没有合适的回复，请稍后再试。）」**。也就是说：

> **兜底文案自己会被 `ResponseGuard` 判成 `stage_direction`。**

于是链路成为「主回复有括号 → fallback 文案也有括号 → 落到 `_SAFE_FALLBACK_REPLY`」，
而 `_SAFE_FALLBACK_REPLY` 就是同一句话 —— **玩家看到的没有变化**。

⇒ 「6/6 全兜底」的准确含义是 **「主回复撞了格式 Guard，兜底这一级又撞了它自己的 Guard」**，
不是「重试没救回来」。这也解释了那组 warning 为什么整齐得像固定模板。

### 7.4 那对括号**不该改**（我 §7.3 初稿的定性是错的）

我一度把这写成「兜底文案违反了 Guard 自己的规则」的自相矛盾。**读了 `config.py` 才知道
括号是有意设计**：

> 2026-09-26：**不带任何角色名**。原值是「Rasmodia：暂时没有合适的回复，请稍后再试。」——
> 兜底不是任何一个角色的台词（哪个 NPC 都可能触发），署名一个具体角色会让玩家以为
> 那句话是法师在说话。**改成括号形态，把它和角色台词在形状上分开。**

| 问题 | 判断 |
|---|---|
| 改掉那对括号？ | **不改** —— 它正是「让系统提示在形状上区别于角色台词」的手段，去掉就退回 09-26 要修的坑 |
| 改 Guard 判据放过它？ | **不改** —— 兜底文案不经模型生成，检查它没有实际收益，但改共享判据的代价远大于收益 |
| 值得做的 | 在 `app.py` 兜底链路处**加注释**写清这个已知对撞，防止未来误诊（**已做**） |

另外查清了一件更硬的事：`FallbackProvider` 返回的就是 `settings.fallback_reply`，
**和 `_SAFE_FALLBACK_REPLY` 是同一个字符串** ⇒ **默认配置下 `fallback_guarded.accepted`
恒为 False**，那个 `if` 分支只在 `BRIDGE_FALLBACK_REPLY` 被配成别的文案时才可能生效。
所以它不是死代码，但**也从来不是「守卫抓到了坏回复」**。

**教训（与 §7.1 同型）**：我把一个**有意设计**当成了缺陷，只因为没去读它旁边那段注释。
**看到「自相矛盾」时，先查它的来历。**
