# 中文 API 接入与原版对白定制路线

日期：2026-08-30  
研究问题：为 Stardew AI NPC 选择合适的中文 API，并判断能否用原版对白定制出更贴角色的模型。  
范围：官方 API 文档、当前 Bridge 接入代码和已有中文联合索引；本轮不使用 API Key、不发送项目资料、不启动训练。

## 结论

### API 推荐

当前最适合先接入的是阿里云百炼的 **`qwen-plus-character`**：它官方定位就是拟人化角色、游戏 NPC 和 IP 复刻，支持 32K 上下文，华北 2（北京）目录价为输入 ¥0.80/百万 Token、输出 ¥2.00/百万 Token，支持上下文缓存。它的官方页面同时标注“模型调优：不支持”，所以它适合做质量对照和在线推理，不适合直接在平台上训练定制版本。

便宜控制组可以用 `qwen-flash-character` 或其固定快照 `qwen-flash-character-2026-02-26`。前者适合短上下文，华北 2 价格为输入 ¥0.25、输出 ¥1.50；快照页面列出的上下文为 262K、输入 ¥0.18、输出 ¥1.50。它们仍然是在线角色模型，不代表一定比本地 9B 更贴 Stardew。

DeepSeek V4 Flash 和 Kimi API 都可以接，但它们是通用模型，不是角色专用模型：前者适合作为低价控制组，后者适合长上下文中文对照。它们不应先于 `qwen-plus-character` 做第一质量实验。

OpenAI 目前不适合作为本项目的定制模型路线。官方模型优化文档写明微调平台正在收缩、对新用户不再开放；当前 SFT/DPO 支持列表主要是 GPT-4.1 系列，并不是 GPT-5.6 Terra/Luna。因此 Terra 可以作为外部老师或质量基准，但不能假设它能直接被训练成一个定制 API 模型。

### 能否用原版对白定制模型

**可以，但“把原版对白全部喂进去”不是正确做法。** 最可靠的路线是：

```text
原版对白审计
→ 条件化行为样本
→ 少量人工审核的 user → assistant 对
→ 先做 RAG/Prompt 对照
→ 再做 LoRA/QLoRA 小规模训练
→ 用固定场景 A/B 和人工盲评决定是否采用
```

原版对白本身主要告诉模型“这个 NPC 怎么说话”，并不完整告诉模型“玩家在什么关系阶段、什么地点、什么渠道问了什么，以及 NPC 应该如何承接”。因此训练样本必须补齐 NPC、关系阶段、时间地点、剧情状态、远程/面对面渠道、当前话题、最近历史、玩家输入和 NPC 回复。

## 三种定制层级

### 第一层：RAG + Prompt，当前最应该继续做

把原版对白当作有来源、可按条件筛选的语气证据；把行为卡、关系阶段、渠道规则和少量成对示例作为执行约束。当前项目已经有中文联合索引、`ContextBuilder`、`PromptBuilder`、行为样本和历史约束，这层最容易回滚，也最适合修复：

- Shane 初识阶段冷淡、短答、必要时结束聊天；
- Sophia、Alex 等角色的不同主动方式；
- 远程邀约与面对面承接；
- 不要为了引用语料而机械回扣同一件事；
- Wizard/Rasmodia 使用一个 canonical `Wizard` 身份；
- 未发生的事件和未确认的承诺不被写成事实。

这一层不需要上传完整原文库，API 请求只携带当前 NPC 必要的几条证据和脱敏状态。

### 第二层：老师模型蒸馏，值得做但必须人工审核

可以让 Terra 或 `qwen-plus-character` 根据“原版证据 + 行为卡 + 场景约束”生成候选成对样本，再由人工筛选。这比直接把云端回复当作角色资料安全得多。

每条样本至少应包含：

```json
{
  "npcId": "Shane",
  "channel": "face_to_face",
  "relationshipStage": "acquaintance",
  "scene": "鸡舍",
  "history": [],
  "playerInput": "今天鸡舍忙吗？",
  "assistantReply": "还行。没着火，就算顺利。",
  "status": "human_approved",
  "sourceRefs": ["...原版对白证据..."]
}
```

初始试验建议先做五个角色各 200～400 条高质量样本，而不是继续批量生成几千条未经审核的句子。样本要覆盖直接回答、回避、拒绝、接受关心、提出邀约、承接上一轮、结束聊天和关系阶段变化；每条只教一个清晰行为。

### 第三层：本地 LoRA/QLoRA，真正做出定制模型

这条路线可行，但不能直接对 Ollama 里的 Q4 模型训练。需要下载对应的 Hugging Face 基础模型，使用 QLoRA/LoRA 训练，再转换或导入 Ollama。

- 当前 8GB 显存机器更适合先对 4B 做可行性试验；9B 训练需要更谨慎的量化、批大小和梯度累积，必要时使用远程 GPU。
- 不建议为每个 NPC 单独训练一个模型；更合理的是共享一个小适配器，样本中明确 `npcId`、关系阶段、渠道和回应动作。
- 只用原版单句对白会导致模型学到词汇和句式，却学不会多轮上下文、冷淡/拒绝和邀约承接。
- 如果需要 DPO，必须为同一输入准备“更符合角色”和“更差/更机械”的成对回复，并保留人工选择依据；不能把模型随机生成的两句直接当偏好标签。

## 推荐给本项目的实际顺序

1. **先接 API 做质量基准**：使用 `qwen-plus-character`，与当前本地 `qwen3.5:9b` 对相同的五角色 × 三场景固定案例；同一份中文联合索引、同一段历史、同一输出上限、同一渠道和关系阶段。云端只作为可选 Provider，不改默认本地路由。
2. **先看 API 是否解决核心问题**：重点评价角色辨识度、星露谷短对白感、中文自然度、阶段/渠道正确性、历史承接和拒绝能力，而不是回复是否更长。
3. **再整理训练数据**：从原版索引提取证据，补齐条件和玩家输入；生成候选后只把人工确认的样本标为 `human_approved`，不把旧网页记录或自动生成结果写回角色资料。
4. **最后做本地适配器**：若 RAG + Prompt 和 API 基准仍不能稳定达到目标，再用小规模人工数据对 4B/9B 基础模型做 LoRA/QLoRA，并使用同一套固定案例比较 base、adapter 和 API 三者。
5. **默认模型的决定放到最后**：只有当 API 或适配器在角色声音和中文自然度上稳定提升，同时没有增加魔法乱入、关系越界、机械回扣和上下文断裂，才考虑用于远程聊天或高质量模式；面对面聊天仍优先低延迟本地链路。

## 不应采用的做法

- 把 7,108 条原文全部塞进每次请求，靠长 Prompt 代替条件检索；
- 只根据模型名称里的“Chinese”“Roleplay”判断中文质量；
- 把云端模型未经审核的回复直接加入 `behavior-examples.json`；
- 用过去测试中的坏回复训练模型；
- 用一个“神秘、活泼、冷淡”等形容词长段落代替可执行行为规则；
- 把完整存档、用户个人数据、API Key 或完整本地路径发送到云端；
- 直接把 Terra/Luna 当成可在 OpenAI API 中微调的目标模型。

## 成本与隐私边界

阿里云角色模型官方页面当前列出的北京价格足以支持小规模 A/B；以本项目短回复和有限历史为前提，真正成本主要取决于每轮输入历史长度、缓存命中和重试次数。第一轮只测固定案例，不开启云端长期记忆，避免模型变量和记忆变量同时变化。

API Key 只从本地环境变量或未纳入 Git 的 `.env.local` 读取。上传到 API 的内容应限制为当前角色必要的结构化状态、少量原版证据和测试输入。原版游戏对白及内容包文本如要随模型或项目公开发布，还需要另外确认游戏和内容包的授权边界。

## 限制

- 本轮没有使用 API Key，没有把任何项目资料发送给 Terra、阿里云或其他第三方。
- 本轮没有实际调用 `qwen-plus-character`，所以不能声称它已经比本地 Qwen 更贴角色。
- API 价格、免费额度、模型版本和微调政策会变化，接入前需要重新查看官方页面和账号实际可用状态。
- 训练是否值得做，最终仍取决于人工审核样本质量和固定案例 A/B；原文数量本身不能保证角色模仿效果。
