# Rasmodia/Wizard 角色语料与说话风格设计

## 状态

- 状态：设计已获用户确认，等待书面规格审阅
- 日期：2026-08-25
- 范围：第一阶段深挖 Wizard / SVE Wizard / Rasmodia，其他角色只建立采集骨架
- 关联能力：角色档案、故事记忆、上下文投影、Provider 回复生成

## 1. 背景与目标

当前对话系统已经能够根据季节、天气、时间、关系阶段和近期消息生成受控的本地演示回复，但 Rasmodia 的背景故事、来源边界和说话风格仍然主要依赖人工编写的简化 profile。仅靠一张静态 persona 表，容易出现以下问题：

- 原版 Wizard、SVE 内容和 Rasmodia Mod 内容互相混用；
- 关系阶段变化时语气变化不明显；
- 角色会把未触发的事件、秘密或推断内容说成确定事实；
- 训练或提示上下文塞入过多原始文本，导致回复机械复读或失去当前场景重点；
- 游戏内表现与语料预览工具之间缺少可追溯的来源关系。

本设计的目标是建立一条可复制的“资源采集 → 来源标注 → 事实与语气分析 → 审阅 profile → 上下文检索 → 回复评测”管线，并先用 Rasmodia/Wizard 这一最难角色完成纵向闭环。

## 2. 范围与非目标

### 2.1 第一阶段范围

深度处理以下来源和场景：

1. 原版 Stardew Valley 的 Wizard 核心文本与已确认背景；
2. SVE 对 Wizard/Magnus 的身份、事件和对白扩展；
3. Rasmodia Mod 对姓名、性别、关系线、对白和事件的覆盖或新增；
4. 日常、季节、天气、节日、事件、商店/任务、信件、婚后和室友等上下文；
5. 关系阶段从初识到婚后/育儿的语气差异；
6. 在游戏运行时已确认的事件、关系和玩家提供事实。

其他 NPC 只建立相同的提取记录结构和索引接口，不在本阶段逐个完成背景和语气精修。

### 2.2 非目标

- 不把完整游戏原始文本提交到 Git 或发送到外部服务；
- 不用模型自动创作未经来源支持的“官方背景”；
- 不让模型控制游戏状态、触发事件或修改关系值；
- 不在本阶段替换真实 AI Provider；
- 不以“所有 NPC 一次性完成”为验收条件。

## 3. 角色身份与来源优先级

角色资料采用分层模型，保持来源可追溯：

1. 原版 Wizard 核心层：原版身份、已确认经历、基础对白和基础关系语义；
2. SVE 覆盖层：SVE 新增或改写的身份、事件、地点和对白；
3. Rasmodia 覆盖层：Rasmodia 的姓名、性别、代词、关系线、专属事件和对白；
4. 运行时事实层：当前日期、时间、天气、关系阶段、已经发生的事件和会话记录；
5. 推断层：由多条证据归纳出的低置信度风格特征，不得伪装成剧情事实。

同一字段出现冲突时，优先级为：

`运行时已确认事实 > Rasmodia 覆盖 > SVE 覆盖 > 原版核心 > 推断`

覆盖不会删除低层来源。系统应保留全部候选记录、来源引用和覆盖关系，以便审阅和回归测试。

## 4. 数据模型

### 4.1 原始语料记录

原始记录保存提取时的最小可追溯单元：

```json
{
  "npcId": "Rasmodia",
  "sourceMod": "Rasmodia",
  "sourcePath": "Characters/Dialogue/...",
  "sourceKey": "...",
  "text": "原始对白",
  "language": "zh-CN",
  "conditions": {
    "season": "summer",
    "weather": "rain",
    "relationshipStage": "friend"
  },
  "evidenceKind": "daily_dialogue",
  "extractionVersion": "..."
}
```

原始语料和绝对本机路径只保存在 `data/generated/` 等本地生成目录，并保持 Git 忽略。

### 4.2 背景事实记录

每条事实至少包含：

- 稳定 `factId`；
- 主体和摘要；
- 来源引用列表；
- 可信度；
- 适用条件；
- 知识范围；
- 是否允许以确定语气输出。

知识范围至少区分：

- `canon_confirmed`：来源明确确认；
- `runtime_confirmed`：当前存档或运行时确认；
- `player_provided`：玩家本次提供；
- `inferred_style`：由语料归纳的风格，不是剧情事实；
- `unverified`：存在但不能直接断言。

### 4.3 说话证据记录

说话样本保留原文和来源，同时附加可审阅标签：

- 场景：日常、节日、事件、婚后、信件等；
- 关系阶段；
- 情绪：疏离、好奇、警惕、关心、幽默等；
- 话题：魔法、星象、塔、自然、承诺、边界等；
- 语气特征：直接性、术语密度、隐喻、回避、情绪转折等。

## 5. Rasmodia 语气档案

最终 profile 保持精简、可人工审阅，不内嵌完整原始语料。第一版语气档案应覆盖：

- 称呼和自称习惯；
- 句子长度、结论顺序和标点倾向；
- 魔法/研究话题的专业术语使用；
- 对未知和危险内容的保留、转述和拒答方式；
- 关心、警惕、怀疑、拒绝和幽默的表达方式；
- 各关系阶段的开放程度、话题池和边界；
- 不同情绪下的表达变化；
- 每项结论对应的 3～6 条代表样本来源。

Prompt 只接收精简语气卡和少量带来源样本，不直接接收整套原始对白。

## 6. 处理管线

```text
本地原版/SVE/Rasmodia 资源
        ↓
提取器（保留路径、键名和来源）
        ↓
本地原始语料库
        ↓
条件规范化与去重（不丢来源）
        ↓
事实/说话证据分类
        ↓
Wizard/Rasmodia 人工审阅 profile
        ↓
profile index 与受限检索
        ↓
ContextBuilder / PromptBuilder
        ↓
FakeProvider 或真实 AI Provider
        ↓
自动回归 + 人工对比评测
```

提取器优先使用已安装的本地资源，记录缺失来源和解析警告；不把“没有找到”转换成“没有发生”。

## 7. 上下文投影规则

每次回复只投影与当前请求相关的最小上下文：

1. 当前运行时事实；
2. 当前关系阶段对应的开放程度与边界；
3. 当前场景、天气、时间和玩家已提供事实；
4. 少量相关背景事实；
5. 3～6 条语气证据样本；
6. 明确禁止断言的未知内容。

未触发事件、没有证据的秘密、仅由模型猜测的预言和其他 NPC 的未公开信息不得作为确定事实输出。

## 8. 异常处理与安全边界

- 资源缺失或损坏：按来源记录 warning，继续处理其他来源；
- 多 Mod 修改同一键：保留全部候选，并显式记录优先级；
- NPC ID 与显示名歧义：使用稳定内部 ID，另存别名映射；
- 翻译、变量或条件无法解析：保留原键和未解析标记，不自行编造；
- 事实来源不足：降低可信度，并从“可确定陈述”检索中排除；
- 原始语料、绝对路径、Token、Cookie 和运行状态不得提交；
- Provider 仍只能生成回复，不得通过角色资料改变游戏状态。

## 9. 测试与验收

实现前先补能够证明目标行为的测试：

### 提取与来源

- 原版 Wizard、SVE、Rasmodia fixture 能被识别；
- source key/path/npcId 保留；
- 同键覆盖不丢失来源；
- 缺失资源只产生可见 warning。

### 事实与边界

- `runtime_confirmed` 能覆盖静态候选；
- `unverified` 不会进入确定事实提示；
- 未触发事件和他人秘密不会被检索为事实；
- 玩家输入的身份、物品和事实不会被错误升级为系统事实。

### 语气与检索

- 关系阶段检索到不同的开放程度和语气卡；
- 天气、时间、研究、危险魔法、隐私等场景能命中对应样本；
- 检索数量受限，不会把整套对白塞入 Prompt；
- Wizard/Rasmodia 不会退化为通用 NPC 语气。

### 人工验收

准备 20～30 条覆盖不同关系阶段和场景的对话，进行并排检查，重点观察：

1. 是否像 Rasmodia，而不是普通模板 NPC；
2. 是否能区分原版、SVE 和 Rasmodia 来源；
3. 是否会把未知剧情说成已经发生；
4. 是否保留克制、古雅、专业且有边界的表达；
5. 游戏内回复与预览工具是否一致。

## 10. 分阶段交付

### 阶段一：资源盘点与最小 fixture

完成 Wizard/SVE/Rasmodia 资源清单、来源映射和最小提取测试。

### 阶段二：背景事实与语气证据

生成本地语料，完成 Rasmodia 时间线、知识边界和关系阶段语气卡的首轮审阅。

### 阶段三：索引与 Prompt 投影

把审阅后的事实和语气卡接入现有 profile index、ContextBuilder 和 PromptBuilder。

### 阶段四：回归与游戏验证

运行 Bridge/SMAPI 测试、预览工具对比和 FastTest 游戏验证，确认实际加载的新 DLL 与新 profile 数据。

## 11. 明确取舍

选择“先深挖 Rasmodia/Wizard”而不是一次性完成所有 NPC，原因是：

- 能优先解决最难的角色一致性问题；
- 可验证来源分层和知识边界是否真正有效；
- 形成的 schema 和测试可以直接复制给其他角色；
- 避免自动聚类把原版、SVE 和 Mod 内容混成一套不可靠人设。
