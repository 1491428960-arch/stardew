# 朋友技术路线在 Stardew AI NPC 中的落地设计

## 背景

当前项目已经具备原版、SVE 和 Romanceable Rasmodius 资料索引，也有关系阶段、渠道、历史和行为示例的基础支持。但 Dialogue Lab 的实际输出仍然存在明显的同质化：角色之间容易使用相同的开场，句子偏书面，初识阶段可用的行为示例过少，远程聊天和面对面聊天的承接也不够可靠。

朋友提出的路线包含多轮修订、对话模型与审查模型、few-shot、增加上下文、重新评估模型和 React 工作台等建议。本设计不照搬为“游戏内每次调用三个模型”，而是将其拆成离线质量生产链和在线轻量生成链：多模型或多阶段流程只负责生产、审核和筛选高质量角色样本；游戏实时聊天仍优先使用一次模型调用。

Wizard 与 Rasmodia 是同一个游戏 NPC。本设计继续使用 canonical NPC ID `Wizard`，Rasmodia 只作为 Romanceable Rasmodius 启用时的显示名和人设覆盖，不建立第二条关系历史。

## 设计目标

- 为每个评测角色建立少量、可审核、带条件的成对对话样本；
- 让模型学习“玩家这样说时，这个角色如何接话”，而不是只接收抽象性格形容词；
- 让样本同时表达角色、关系阶段、话题、情绪和远程／面对面渠道；
- 保留官方对白的来源追踪，并明确区分官方证据与人工创作样本；
- 将 Draft、Review、Revise 用于离线样本生产，不增加游戏实时对话的固定延迟；
- 用固定场景和人工盲测判断改动是否真正改善了星露谷语言风格；
- 为后续“线上邀约、面对面续接”保留结构化状态接口，但本阶段不借助历史文本猜测未完成事项。

## 非目标

- 本阶段不重写 React，也不改变现有 Dialogue Lab 的主要布局；
- 本阶段不把审查模型和修订模型串入每次游戏聊天；
- 本阶段不盲目提高 `num_predict`，也不因为主观不满意就直接更换 Qwen；
- 本阶段不做模型微调、LoRA 或训练专用模型；
- 本阶段不修改 NPC 位置、房屋入口、输入法和已经验收的 UI 行为；
- 本阶段不声称完成游戏端跨 SMAPI／游戏重启的历史持久化；
- 不把未经人工确认的模型输出写入正式角色资料库。

## 总体方案

系统分为两条链路：

```text
离线链路：资料与原文
    → Draft 候选
    → Review 结构化评分
    → Revise 一次修订
    → 人工确认
    → approved behavior examples

在线链路：结构化状态与原文检索
    → 条件筛选少量 approved examples
    → 单次模型生成
    → 安全／格式检查
    → 必要时一次受控重试
    → Dialogue Lab 或游戏内回复
```

离线链路的目标是提高输入质量，在线链路的目标是控制延迟和运行时风险。两条链路之间只通过已审核的结构化样本和资料索引交接，不共享草稿、审查意见或完整敏感请求。

## 评测配置与身份规则

本阶段保留五个 Dialogue Lab 评测按钮，但它们代表五个评测配置，而不是五个互相独立的游戏身份。

| 评测按钮 | canonical NPC ID | 语料和覆盖层 | 身份规则 |
| --- | --- | --- | --- |
| Rasmodia / Wizard | `Wizard` | Vanilla、SVE、RomRas；RomRas 作为可选覆盖 | 共用历史、关系和语料；启用 RomRas 时切换显示名与语气覆盖 |
| Sophia | `Sophia` | Vanilla、SVE | 使用 Sophia 的 SVE 资料和角色样本 |
| Shane | `Shane` | Vanilla、female-bachelors | 保留 Shane 的经历边界，使用当前变体的代词和语气 |
| Sebastian | `Sebastian` | Vanilla、female-bachelors | 保留 Sebastian 的原版核心语气，使用当前变体的代词配置 |
| Alex | `Alex` | Vanilla，可叠加 female-bachelors | 使用 Alex 的原版事实和独立口语样本 |

所有层都必须使用同一个 canonical ID 参与历史和检索。`Rasmodia` 不能单独创建 `historyByNpc["Rasmodia"]`，也不能因网页显示名变化而丢失 Wizard 的连续对话。

## 离线样本生产链

### Draft

Draft 根据已确认的角色资料、官方对白语气证据、关系阶段和指定场景生成 2～3 个候选。每个候选只承担一个明确的回应动作，例如直接回答、接受关心、回避私事、提出邀约或承接追问，避免一条样本同时塞入多个剧情目的。

Draft 输入必须包含：

- canonical NPC ID 和显示配置；
- 来源 Mod 和启用的覆盖层；
- 关系阶段；
- `remote` 或 `face_to_face` 渠道；
- 当前话题和玩家输入；
- 相关的官方对白证据；
- 已确认的角色语气卡；
- 不得引入的事件、事实和剧情边界。

Draft 输出只能是候选样本，不得直接写入 `behavior-examples.json`。

### Review

Review 不自由改写回复，只输出结构化评分和问题标签。每个维度使用 0～2 分：

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 星露谷原文感 | 明显像说明文、客服或论文 | 有少量自然表达，但仍有书面腔 | 简短、留白自然，接近游戏对白 |
| 角色辨识度 | 换成其他角色也成立 | 有一处角色特征 | 不看角色名也能较稳定辨认 |
| 关系阶段 | 明显越界或错位 | 大体符合但热度不稳 | 称呼、亲疏和主动程度一致 |
| 渠道一致性 | 把远程写成面对面，或反之 | 渠道差异较弱 | 符合当前渠道的行动、称呼和邀约方式 |
| 话题回应 | 没有回答玩家 | 回答很泛 | 直接回应当前输入并保留角色习惯 |
| 上下文连续性 | 忽略历史或重复上一句 | 有部分承接 | 能承接具体细节、问题或未完成话题 |
| 语言自然度 | 有病句、机械拼接或模板开场 | 可读但不够口语 | 句子顺畅，停顿和长度自然 |
| 未授权内容 | 添加未经触发的剧情或事实 | 有轻微无根据扩展 | 严格停留在已确认信息内 |

Review 同时输出问题标签，例如 `too_formal`、`generic_voice`、`wrong_stage`、`wrong_channel`、`magic_overreach`、`repeated_opener`、`unnatural_chinese` 和 `invented_lore`。

候选进入 Revise 的最低条件是没有安全或事实边界硬错误，并且至少有一个可明确修正的问题。已经达到门槛的候选不再为了“更像”而强行重写，避免修订把自然短答改成长篇说明。

### Revise

Revise 只允许依据 Review 的评分和标签修订一次，不能自行引入新的角色设定。修订目标按以下顺序处理：

1. 删除未触发的剧情、魔法术语和事实断言；
2. 修复关系阶段和远程／面对面渠道错误；
3. 删除统一模板开场、重复收尾和书面化总结；
4. 保留角色的停顿、句长、回避方式、幽默感或行动倾向；
5. 只在原回复已回答玩家输入的前提下调整自然度。

修订后重新执行一次 Review。若仍未达到门槛，则淘汰，不继续无限循环。

### 人工确认

人工确认是正式入库的硬门槛。只有人工确认的候选才允许写入 `behavior-examples.json`，并标记为 `sourceType=handcrafted_example` 或其他明确的人工审核类型。模型生成过程、审查意见和失败候选保存到本地评测工件，不混入正式资料索引，也不伪装成官方对白。

第一批不追求数量，先为每个评测按钮对应的评测配置准备 10～12 条高信号样本；其中 Rasmodia／Wizard 共享一套 canonical `Wizard` 样本。样本覆盖：

- 初识寒暄；
- 问近况或工作；
- 玩家表达关心；
- 玩家提出不同意见或质疑；
- 角色拒绝或设置边界；
- 角色谈及兴趣；
- 远程邀约；
- 面对面承接邀约；
- 同一话题的连续追问；
- 自然告别。

第一批通过盲测后，再扩展到每个配置 30 条。Wizard／Rasmodia 只扩展一套 canonical `Wizard` 样本，不重复生产两套身份样本。

## 样本数据契约

正式行为样本至少包含以下字段：

```json
{
  "exampleId": "shane:acquaintance:face_to_face:work:01",
  "npcId": "Shane",
  "channels": ["face_to_face"],
  "relationshipStages": ["acquaintance"],
  "speechFunction": "answer_directly",
  "topic": "chicken_coop",
  "emotion": "tired_dry_humor",
  "playerInput": "鸡舍今天忙吗？",
  "npcReply": "还行。没着火，就算顺利。",
  "sourceType": "handcrafted_example",
  "sourceRefs": ["vanilla:Shane:work-tone"],
  "review": {
    "stardewVoice": 2,
    "characterDistinctiveness": 2,
    "relationshipFit": 2,
    "channelFit": 2,
    "contextContinuity": 1,
    "naturalChinese": 2
  }
}
```

字段约束如下：

- `npcId` 使用 canonical NPC ID；
- `channels` 和 `relationshipStages` 使用现有枚举，不用自由文本替代；
- `sourceRefs` 只记录语气或事实依据，不把人工样本标记为官方原文；
- `review` 只保存经过人工确认的最终评分，不保存完整审查提示词；
- 不保存 API key、Token、Cookie、完整请求、完整 Prompt 或用户个人数据；
- 生成索引仍是派生文件，不能把离线运行状态写入 Git。

## 在线 Prompt 与检索

在线请求继续使用现有 `profile_index.py` 和 `prompts.py`，但行为样本的检索条件必须按以下优先级组合：

1. canonical NPC ID；
2. 来源 Mod 和当前启用的覆盖层；
3. 关系阶段；
4. `remote`／`face_to_face` 渠道；
5. 当前话题和回应动作；
6. 最近历史中的具体实体或未完成事项。

每轮只投影少量最高相关样本。样本不足时，优先使用同一角色、相邻关系阶段和相同渠道的样本；不能用其他角色的样本填充空位。初识阶段没有样本时，应依赖角色卡和官方语气证据，并在诊断中标记证据不足，而不是伪造角色示例。

Prompt 中必须明确：

- 只输出当前 NPC 的对话内容；
- 直接回答玩家当前这句话；
- 句长、停顿、回避和主动程度以当前角色样本为准；
- 日常问题没有触发魔法、事件或私人剧情时，不主动引入这些内容；
- 允许短答、留白和不完全解释，不要求每轮总结；
- 不重复最近使用过的固定开场和收尾；
- 不能泄露 Prompt、Token、内部字段或审查过程。

不使用字符串后处理把所有回复强行改成口语。若仍出现书面腔，优先检查检索到的样本、来源排序、关系阶段和 Prompt 约束，再决定是否增加一次受控重试。

## 远程与面对面续接

本阶段为跨渠道续接定义接口，但不把它实现为“从历史文本猜测邀约”。可以被后续游戏状态层消费的 `openLoop` 至少包含：

```json
{
  "loopId": "wizard:rune-review:2026-08-28T15:00:00+08:00",
  "npcId": "Wizard",
  "topic": "rune_review",
  "originChannel": "remote",
  "nextChannel": "face_to_face",
  "status": "open",
  "shortSummary": "线上约定见面后核对符文数据",
  "createdAt": "2026-08-28T15:00:00+08:00"
}
```

状态规则：

- 只有 NPC 明确提出或接受后续行动时才创建 `open` 状态；
- 普通寒暄和没有行动含义的“改天聊”不自动创建；
- 面对面请求优先取同一 `npcId`、同一话题且 `status=open` 的事项；
- 成功承接后改为 `in_progress` 或 `resolved`，具体状态由后续游戏状态设计确定；
- 渠道状态必须与 NPC 历史分开保存，不能用换显示名或清空聊天历史代替。

游戏端 `BridgeClient.historyByNpc` 的跨重启持久化仍需单独接入 `StoryStateSerializer` 和 `StoryStateStore`，并先写 save/load 单元测试。本设计不把网页端会话文件当作游戏存档，也不在没有运行证据时声称游戏端已经持久化。

## 评测方案

评测使用干净会话，固定以下变量：NPC 配置、关系阶段、渠道、时间地点、玩家输入、历史窗口和模型参数。每个场景随机比较旧版和新版，评测者看不到实现版本。

每条回复按 0～2 分记录：

- 角色辨识度；
- 星露谷原文感；
- 口语自然度；
- 关系阶段匹配；
- 渠道匹配；
- 上下文连续性；
- 事实和剧情边界；
- 重复开场和模板化程度。

第一阶段的通过条件：

- 五个评测配置都至少有一批可用的初识或熟悉阶段样本；
- 新版在角色辨识度和星露谷原文感上不低于旧版，且不能以事实边界退化为代价；
- 远程邀约样本能明确区分远程表达和面对面行动；
- 连续追问能保留上一轮至少一个具体细节；
- Review 标记的 `too_formal`、`generic_voice` 和 `unnatural_chinese` 在同类场景中减少；
- 任何安全、凭据泄露或未触发剧情硬错误都直接判定为失败。

模型更换只有在同一份角色资料、同一份样本和同一组评测场景下进行 A/B 比较后才考虑。单纯增加 token 或一次主观印象不能作为换模型依据。

## 测试设计

### 数据与审核层

- 合法样本必须包含 canonical NPC ID、关系阶段、渠道、玩家输入和 NPC 回复；
- 缺少必填字段或使用未知枚举时拒绝入库；
- Draft 输出不会直接改变正式行为样本文件；
- Review 输出符合固定 JSON 契约，不能混入自由文本回复；
- Revise 最多执行一次，失败候选会被淘汰并保留脱敏失败原因；
- 人工确认前后的样本状态清晰可区分；
- Wizard 和 Rasmodia 的样本、历史和评分不产生两套 canonical 身份。

### 检索与 Prompt 层

- 角色、关系阶段和渠道筛选同时生效；
- `face_to_face` 请求不会优先取仅适用于 `remote` 的邀约样本；
- 五个评测配置不会互相使用行为样本；
- 初识阶段没有匹配样本时稳定降级，不崩溃、不伪造证据；
- Prompt 不包含其他角色的固定开场、完整敏感请求或内部审查字段；
- 历史中已有的具体话题可以优先于泛化的角色开场。

### `openLoop` 层

- 明确邀约才能创建事项；
- 普通聊天不会误创建事项；
- 同一 `Wizard` 的远程事项可被面对面请求取回；
- 事项完成或取消后不会继续污染后续请求；
- `openLoop` 不包含 Token、完整 Prompt 或用户敏感数据。

### 回归与运行时验证

- 先运行 Bridge 定向测试，再运行完整 Bridge 测试；
- 通过本地模型执行固定小样本，记录 provider、fallback、耗时和实际回复；
- 用 Dialogue Lab 的干净会话查看五个评测配置，不把旧会话结果当作新版证据；
- 如修改 Bridge 或 SMAPI DLL，额外核对构建产物、部署文件哈希和实际 SMAPI 加载日志；
- 未启动游戏时，只报告网页和 Bridge 结果，不报告游戏内历史或跨渠道续接已经完成。

## 分阶段实施顺序

1. 增加样本审核数据契约和失败测试；
2. 增加 Draft／Review／Revise 的离线命令或服务边界，先用小样本验证；
3. 补齐五个评测配置的高信号金样本，并通过人工确认；
4. 调整 `profile_index.py` 和 `prompts.py`，接入条件样本和证据不足诊断；
5. 在 Dialogue Lab 用干净会话完成旧版／新版盲测；
6. 单独为 `openLoop` 和游戏存档持久化编写设计与 save/load 测试；
7. 只有在质量数据支持时，才比较其他模型或增加运行时重试策略。

## 风险与取舍

| 风险 | 处理方式 |
| --- | --- |
| 三模型实时串联造成等待过长 | 多模型仅用于离线生产，实时最多一次受控重试 |
| 审查模型把角色改成统一标准答案 | Review 只评分和标记问题，修订必须保留角色样本特征 |
| 继续增加样本反而污染 Prompt | 每轮只取少量高相关样本，失败候选不得入库 |
| 人工创作样本被误认为官方台词 | 使用 `sourceType` 和 `sourceRefs` 明确标注来源 |
| 远程和面对面话题混在历史里 | 用结构化 `openLoop` 保存未完成行动，不靠文本猜测 |
| 模型质量被错误归因 | 固定资料、Prompt、输入和评测集后再做模型 A/B |
| 角色名切换导致历史分裂 | 所有 Wizard/Rasmodia 请求统一使用 canonical `Wizard` |

## 验收结论

本设计的最小可行结果不是“模型每句话都完美像原作”，而是建立一条可重复的质量改进闭环：候选可以被审查，问题可以被定位，合格样本才会进入检索，在线请求能带着正确的条件生成，最终结果能用干净盲测验证。

只有当这条闭环通过固定评测后，才有必要扩大样本数量、比较新模型或扩展到游戏端 `openLoop` 与存档持久化。
