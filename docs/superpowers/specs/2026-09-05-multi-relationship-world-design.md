# 复数恋爱与婚姻世界观设计

## 目标

为主角同时与多个 NPC 恋爱、结婚和共同生活建立稳定的世界观与对话规则。复数关系在法律和社会政策层面是合法且可被理解的，但星露谷仍保留战前形成的一夫一妻生活习惯。NPC 不会因为主角拥有其他伴侣就自动否定关系，也不会因此失去自己的嫉妒、不安、比较心理和边界。

第一阶段只处理“主角—单个 NPC”的关系边，不实现多人同场调解，也不推断 NPC 之间自动建立恋爱关系。每个 NPC 分别维护自己的关系阶段、已知信息、接受程度和情绪状态，主角再通过多次一对一对话处理这些关系。

成功标准：

1. NPC 不会在缺少信息时表现得像全知视角，也不会把主角没有主动广播关系误判成欺骗。
2. 婚礼结束后，主角与该 NPC 的婚姻关系成为社区公共事实；恋爱关系仍然可以只在局部生活圈中传播。
3. NPC 能在接受复数关系制度的同时，因为时间、陪伴、承诺履行或亲密表达失衡而自然吃醋。
4. 关系阶段和信任经历影响 NPC 是否愿意讨论、尝试或接受复数关系，但不直接强制任何 NPC 接受。
5. 调解只通过主角与单个 NPC 的一对一对话发生，结果可以是接受、有条件接受或暂时无法接受。
6. 五个目标角色保留各自的表达方式；自动诊断能区分世界观接受度、当前嫉妒和正常角色差异。

## 背景与社会规则

### 1. 战后政策

战争造成了人口结构、照护责任和家庭继承方面的问题。战后政策因此承认复数恋爱和婚姻，提供与婚姻相关的居住、继承、照护和家庭权益保障。政策解决的是法律资格和社会安全，不代表所有人都选择复数关系。

### 2. 星露谷地方文化

星露谷是熟人社会，镇民的生活经验仍然更接近传统的一夫一妻。大多数人会把一对一婚姻当作最熟悉的默认模式，但不会把复数关系视为违法或道德上不可接受的事情。

因此，NPC 可以同时表达以下两种看法：

- “我知道这在法律上很正常。”
- “但我不确定自己能不能这样生活。”

政策接受度、个人参与意愿和当前情绪必须保持独立。NPC 不愿意进入复数关系时，可以拒绝或暂缓，不应被写成反派，也不应被系统判定为角色质量失败。

## 关系事实与信息可见性

### 1. 客观关系事实

世界状态保存主角与每个 NPC 的客观关系，包括恋爱、订婚、婚姻、关系开始时间和公开事件。客观事实不因为某个 NPC 尚未得知而消失，也不因为传闻而被改写。

### 2. NPC 视角信息

每个 NPC 只获得自己通过生活交集取得的关系信息。信息应记录事实、来源、获得时间和确定程度，至少区分：

- `known`：NPC 已经明确知道；
- `suspected`：NPC 根据观察或传闻产生怀疑；
- `unknown`：NPC 尚未接触到相关信息。

恋爱关系默认是局部知情：恋爱对象本人一定知道，朋友、共同活动参与者和经常观察到两人的人可能知道，其他 NPC 不会自动同步。主角不需要向所有人广播每一次约会，但不能伪造单身状态，也不能在被直接问到时撒谎。

婚姻关系通过婚礼公开。婚礼结束后，主角与该 NPC 的婚姻事实进入社区公共认知；没有参加婚礼的 NPC 可以稍晚通过消息得知细节，但不能长期保持“完全不知道这场婚姻存在”的状态。

订婚或公开宣布属于比普通恋爱更高的可见度事件，但仍不要求每个 NPC 同时收到完整信息。信息差应来自接触范围和时间，不来自系统故意制造虚假事实。

### 3. 间接消息与误解

间接消息可以不完整，也可以被 NPC 误解，但第一阶段不制造完全虚假的世界事实。例如：

- NPC 看到主角和 Sophia 经常在酒窖见面，只能确定两人亲密，不能自动确定已经结婚；
- NPC 听说主角“最近总和 Sebastian 待在一起”，可以产生怀疑，但不能把传闻直接当成婚姻事实；
- NPC 直接询问主角时，主角的回答决定其是否从 `suspected` 进入 `known`；
- NPC 的错误推断可以造成短期情绪，但在事实澄清后不应继续被当作客观关系记录。

## 关系阶段与个人接受度

复数关系接受度不是全局开关，而是每个 NPC 的个人状态。关系阶段决定 NPC 是否愿意深入讨论，信任和共同经历决定调解是否有基础，个人边界决定接受之后怎样相处。

建议使用以下概念层级：

| 关系阶段 | 默认叙事能力 |
| --- | --- |
| 初识、熟悉 | 可以理解政策，但通常不愿意把自己代入复数关系；对主角其他关系只做有限反应。 |
| 朋友 | 可以讨论价值观和生活选择，但可能明确表示自己不会这样恋爱。 |
| 亲近 | 有足够信任进行一对一坦诚交流，可能从排斥转为考虑。 |
| 恋爱 | 新增伴侣会直接影响安全感、时间分配和承诺，需要通过具体相处建立信任。 |
| 婚后 | 已有共同生活基础，接受协商的可能性更高，但不代表自动免疫嫉妒。 |

阶段只影响“是否能谈、是否有机会接受和需要多少信任”，不直接决定结果。每个 NPC 至少需要表达以下三类状态：

- `accepted`：接受主角存在其他关系，并愿意继续共同生活；
- `conditional`：接受，但要求明确的时间、公开和亲密边界；
- `not_ready`：当前无法接受，可以继续观察、暂缓或退出恋爱关系。

调解后的接受也不是永久情绪豁免。NPC 仍可能因为连续失约、被比较、亲密表达明显失衡或长期得不到独处时间而再次吃醋。情绪恢复依靠回应、解释、履约和后续相处，而不是把状态强制重置为“无嫉妒”。

## 一对一调解流程

### 1. 触发条件

NPC 得知主角新增伴侣后，可以主动发起一对一关系协商，也可以先通过普通对话试探、观察或暂时不谈。系统不强制每段新关系都立刻触发调解。

调解触发至少需要保留：

- NPC 当前知道或怀疑的关系事实；
- 当前关系阶段；
- 与主角的信任和共同经历；
- 触发情绪的具体事件；
- NPC 自己的个人边界和当前承受能力。

### 2. 协商内容

一对一对话只讨论该 NPC 与主角自己的关系，不要求 NPC 代表其他伴侣发言。可讨论：

- 是否知道主角的其他恋爱或婚姻关系；
- 是否愿意尝试复数关系；
- 希望如何分配固定相处时间；
- 节日、夜晚和共同活动的安排；
- 哪些亲密表达会造成比较或不安；
- 出现嫉妒时希望主角如何回应；
- 是否接受公开共同生活，或希望保留独立空间。

多人会议、让一个 NPC 替其他 NPC 做承诺、自动生成 NPC 之间的浪漫关系均不在第一阶段范围内。

### 3. 结果与后续

调解结果可以是接受、有条件接受或暂时无法接受。结果必须写回该 NPC 自己的关系状态，不能自动覆盖其他 NPC 的接受度。之后的普通对话继续读取该 NPC 的已知信息和边界；新事件可以产生新的嫉妒，但不应反复触发同一段“首次发现”剧情。

## 对话行为与角色化要求

NPC 的吃醋要针对具体关系体验，而不是否定世界政策。生成约束按以下优先级执行：

1. 先回答当前玩家输入和场景；
2. 只使用该 NPC 已知或合理怀疑的信息；
3. 根据关系阶段和个人边界表达接受、疑问、嫉妒或需要空间；
4. 给出一个角色化的具体需求、行动或协商入口；
5. 玩家已经安慰、解释或回应后，不重复发起同一轮指责。

五个目标角色的人工验收可使用以下方向作为示例，不把它们变成统一模板：

- Rasmodia / Wizard：偏向分析承诺、时间和共同生活安排，可能把嫉妒转化为理性协商；
- Sophia：更容易直接表达不安或需要陪伴，但仍保留温柔和具体生活细节；
- Shane：可能嘴硬、低落或短暂收口，需要允许自己要空间，不强制追加浪漫表达；
- Sebastian：更克制，可能减少话语、通过音乐或独处表达反应，不自动公开制造冲突；
- Alex：可能用竞争、打趣或行动邀约表达“我也想占据你的时间”，但不能把所有吃醋都写成攻击。

这些差异必须服从各自的 canonical persona、当前关系阶段和已有故事状态。复数关系政策不能覆盖角色原本的疲惫、内向、外向、研究者气质或生活兴趣。

## 数据流与边界

推荐的数据流如下：

1. 世界事件更新主角与 NPC 的客观关系事实；
2. 公开事件或生活交集更新对应 NPC 的视角信息；
3. 当前 NPC 的 Prompt 只投影自己的已知事实、怀疑、关系阶段、接受状态和最近情绪；
4. 一对一对话产生回复和可解释的关系事件；
5. 事件只更新参与对话的 NPC，除非发生了婚礼或其他明确公开事件；
6. 后续对话使用更新后的该 NPC 状态，并保留其他 NPC 的独立视角。

安全边界：

- 缺少视角信息时，NPC 使用不知情或不确定表达，不得凭空补全关系事实；
- 信息来源冲突时，保留不确定状态，等待主角直接说明或公开事件澄清；
- 直接询问不得被生成器改写成主角自动撒谎；
- 明确拒绝、需要空间和自然收口不得因为“缺少亲密表达”触发浪漫重试；
- 任何 NPC 的接受结果都不能自动同步给其他 NPC；
- 不把嫉妒、迟疑或暂时无法接受标记为 Provider 错误或格式错误。

## 测试与评测

测试按四层组织：

1. 世界规则测试：战争政策允许复数关系；星露谷默认文化仍偏一夫一妻；婚礼使婚姻事实公开；普通恋爱不自动全局同步。
2. 视角测试：同一客观关系在不同 NPC 处分别呈现 `known`、`suspected` 和 `unknown`；没有信息的 NPC 不得全知；直接询问后能从怀疑变为明确知道。
3. 阶段和调解测试：初识、朋友、亲近、恋爱和婚后对同一事件产生不同可谈程度；一对一调解能得到 `accepted`、`conditional` 和 `not_ready`，且不会改写其他 NPC 状态。
4. 多轮质量评测：五个角色各覆盖未知信息、部分得知、直接询问、轻微吃醋、调解后协商和恢复沟通；同时覆盖远程、当面、已有历史和收口场景。

重点负例：

- NPC 没有见过或听过另一段恋爱，却直接说出完整关系表；
- NPC 把普通共同活动直接断言为婚姻；
- NPC 因主角拥有其他配偶而直接道德审判或退出，且没有个人边界依据；
- 调解成功后每轮都重复吃醋；
- Shane 在明确需要空间后被强制追问浪漫承诺；
- Sebastian、Alex、Sophia 或 Wizard 被统一改写成同一种嫉妒语气；
- 一名 NPC 的不知情状态因为另一名 NPC 得知信息而自动同步。

人工验收不只看是否出现“吃醋”词语，还要检查角色是否回应了当前对象、是否提出了具体需求、是否允许主角解释、是否保留了关系阶段和原始性格。自动评分只用于筛选样本，不单独决定角色是否接受该世界观。

## 第一阶段范围与回滚

本阶段包含关系事实与 NPC 视角拆分、公开婚姻事件、局部恋爱信息、一对一调解状态、嫉妒事件和五角色评测样本。

本阶段不包含 NPC 之间自动恋爱、多人会议、全镇关系网络可视化、复杂法律手续、多人共同 Prompt、强制所有角色接受或把评测生成结果写回角色资料库。

回滚时只移除本阶段新增的关系字段、视角投影、调解状态、嫉妒诊断和测试样本，不触碰既有角色资料、正式 Mods、存档、旧评测工件、API Key 和 `qwen3.5:9b` 回退配置。

## 实现前验证要求

实现前先为以下行为建立红灯测试：

1. 婚礼后公共婚姻事实可被社区视角读取；
2. 普通恋爱事实不会自动同步给所有 NPC；
3. 缺少信息的 NPC 不会全知；
4. 一对一调解只更新参与的 NPC；
5. 调解后的接受状态不会阻止后续合理嫉妒；
6. 明确需要空间或收口时不会触发浪漫重试。

实现后先运行相关 Python 定向回归，再运行 Bridge 全量回归；新 Gemini 评测必须使用独立工件目录，先小批次确认评分契约，再决定是否进行完整批次。整个实现阶段不启动游戏、不部署 DLL、不修改正式存档或角色资料库，也不输出任何 Key、Token 或完整 Prompt。
