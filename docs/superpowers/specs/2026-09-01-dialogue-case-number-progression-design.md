# 角色质量案例编号与多轮推进设计

## 背景

当前案例浏览器已经能显示三轮结果和关系阶段，但案例只有 `caseId`，人工反馈时不便定位。自动评分也按单轮判断：如果三轮回复围绕同一语义反复改写，只要各轮碰巧命中词，完整案例仍可能被看成通过。

上一批人工复核还暴露出婚后案例的问题：部分玩家输入像评测脚本，三轮之间没有自然推进；婚后回复虽然不越界，却缺少已建立亲密关系后的靠近、邀约和自愿确认。

## 目标

1. 为 `DEFAULT_CASES` 固定顺序生成稳定的 `#1` 起始编号，并让 API、案例列表、详情和结果都能显示它。
2. 在保留单轮评分的同时增加完整三轮的推进检查：相邻 NPC 回复不能只重复上一轮的主要表达；每轮应带来新的具体动作、态度、细节或明确收口。
3. 重写五个婚后案例的玩家输入、关系说明和续聊意图，使三轮输入更像自然对话，并显式覆盖亲密推进而不是只测家务或物件。
4. 在结果中同时报告单轮通过数量/比例和完整案例通过数量/比例，旧工件仍可读取。

## 设计

### 1. 稳定编号

编号不写入案例定义，避免手工维护错位；`quality_case_catalog()` 按 `DEFAULT_CASES` 顺序用 `enumerate(..., 1)` 输出 `caseNumber`。评测脚本在结果记录中写入同一编号，脱敏读取器保留非负整数。页面用 `#编号` 放在列表、详情标题和案例定位栏，筛选不会重新编号。

### 2. 多轮推进评分

新增纯函数 `score_dialogue_progression(replies, turns)`。它只接收生成的 NPC 回复和当前案例轮定义，使用规范化文本、相邻回复的字符 n-gram 重合度及当前轮 `expected_terms` 是否引入新证据来识别重复。至少两轮成功回复且相邻回复高度重复、同时没有新的当前轮证据时，为后一个轮次添加 `repeated_turn_content`；回复短但明确拒绝或收口时不因长度本身失败。

评测脚本在所有轮次生成后再应用序列标签：单轮 `score.passed` 保持原语义，但重复推进会让对应轮次和完整案例标记为需复核。结果增加 `progression`、`progressionTags`、`casePassed` 和通过轮数；摘要增加 `passedTurns`、`turnPassRate`、`passedCases`、`casePassRate`，同时保留旧 `passed` 字段作为完整案例通过数兼容字段。

Prompt 在存在真实 assistant 历史时加入短的 `progression_guard`：当前输入若延续前文，要新增一个具体进展或明确收口，不能只改写上一句；拒绝或结束聊天是允许的，不要求所有角色强行延长。

### 3. 婚后案例

Wizard/Rasmodia、Sophia、Sebastian、Alex 的婚后案例以及 Sebastian 的共同生活案例，都改成三步递进：先提出陪伴或亲密意图，再对场景中的具体行动作出回应，最后在双方自愿的前提下确认靠近、独处或收尾。文本保持非露骨成人亲密，不把强度标签写进对白，不凭空新增剧情事实。

## 错误处理与兼容

- 回复不足两轮、Provider 中途失败或旧结果没有序列字段时，页面显示已有结果，不伪造推进通过。
- 序列检查只产生标签，不改写模型回复。
- `quality_results` 继续过滤 prompt、Token、API key 等敏感字段，并兼容旧 `schemaVersion` 和没有 `caseNumber`/`progression` 的工件。
- 不发起 API 请求直到自动化测试和页面结构检查通过；新云端批次使用独立目录，不覆盖旧批次。

## 验收

- 定向测试先出现预期红灯，再在实现后通过。
- Bridge 完整测试、Python 语法检查和 `git diff --check` 通过。
- `/api/quality/cases` 编号为连续 `1..N`；`/test` 页面显示编号、序列提示和单轮/完整案例统计字段。
- 独立云端批次能返回三轮结果，并记录单轮与完整案例通过率及实际 Token 用量。
- 浏览器重点查看 #17、#25、#27、#30、#32，确认婚后三轮不再只是同义复读，且测试输入具备自然推进。
