# 「找话题」连续性与主动亲密优化设计

## 背景

上一批 `topic-start-intimacy` 结果暴露的主要问题不是单纯的模型表达偏冷，而是请求语义在多轮之间没有切换：案例级 `intent="topic"` 被三轮复用，后两轮玩家输入被 `PromptBuilder` 清空，模型因此每轮都重新开题。

同时，案例定义中的 `topic` 没有进入生成上下文，测试又把「NPC 自由找话题」和「必须命中固定词」混在一起，导致实际话题、后续输入和评分标准互相错位。

本设计只处理 Dialogue Lab / Bridge 的测试生成与对话质量评测，不写入正式角色资料、不修改正式存档、不部署游戏 DLL。

## 目标

1. 首轮空输入时，NPC 能围绕当前角色、地点、时间和案例话题种子自然开场。
2. 第二、三轮能看到玩家真实输入，并承接最近一轮 NPC 回复中的具体对象或动作。
3. dating / married 目标案例表现出更主动、更热情的亲密推进，同时保留各角色的说话方式和边界。
4. 测试能区分「话题承接失败」「突然换题」「缺少主动亲密信号」和「关系边界越界」，不再只依赖固定关键词命中。
5. 保留少量模糊短答压力测试，同时用明确承接案例作为主要可判定样本。
6. 新结果单独落盘，网页能明确选择并显示新批次；旧批次保持不变。

## 非目标与边界

- 不把所有 NPC 改成统一的甜腻或露骨口吻。
- 不允许把 `topic` 测试元数据伪装成玩家已经说过的话。
- 不生成强迫、非自愿、未成年或关系未成立的成人内容。
- 本轮成人亲密测试保持双方成年、自愿和关系已成立；可以有直接暧昧、亲吻、拥抱、靠近和私下安排，但不生成露骨性行为过程或生殖器细节。
- 不把模型生成的未审核回复写回 `data/personas`、行为样例库或正式记忆。
- 不改变默认 `default` 评测套件的案例数量和网页目录语义。

## 方案选择

### 方案 A：最小修复

只把首轮 `topic` 与后续 `chat` 分开，保留现有历史和评分逻辑。

优点是改动小、回归风险低；缺点是案例中的 `topic` 仍缺少明确的上下文投影，固定期望词仍可能误判自由开场，无法充分解释「承接了什么」。本轮不采用 A 作为完整方案。

### 方案 B：分层请求语义、当前话题约束与双轨评测（采用）

在 A 的基础上增加每轮请求语义、话题种子投影、连续对话 Prompt 契约和针对主动亲密的评分门槛。主测试使用明确承接，压力测试使用模糊短答；两者分别衡量可控连续性和模型在弱输入下的主动维持能力。

优点是同时修复真实输出和测试失真，能够定位「没有看到输入」与「看到了但仍换题」两类问题；代价是需要扩展案例模型、Prompt、评测结果字段和定向回归。

### 方案 C：只重写测试

把后续玩家输入改得更具体，但不修改请求语义和 Prompt。

它只能让评分更容易命中，不能修复网页和真实对话中的多轮 topic 误用，因此不采用。

## 设计

### 1. 多轮请求模型

为 `CharacterQualityTurn` 增加可选的 `intent`，默认沿用案例级 `intent`，保证旧案例兼容。

`topic-start-intimacy` 的三轮语义固定为：

| 轮次 | intent | 玩家输入 | 目标 |
| --- | --- | --- | --- |
| 1 | `topic` | 空字符串 | NPC 主动选择并开启一个具体话题 |
| 2 | `chat` | 明确承接或模糊短答 | 回应玩家并维持当前话题，主动推进一小步 |
| 3 | `chat` | 接住上一轮安排或表达 | 在确认和可商量的前提下温暖收束或提出下一步 |

评测脚本和上下文构造统一使用「当前轮 intent」，不再直接使用 `case.intent` 覆盖全部轮次。只有 `topic` 轮清空生成用玩家输入并发送内部 `topic_trigger`；`chat` 轮必须保留真实玩家输入并发送普通 `player_input`。

### 2. 话题种子与当前话题

案例保留一个面向测试的 `topicSeed`，例如「新歌单」「葡萄园晚风」「月光记录」。它是 NPC 首轮可选择的具体切入点，不是玩家台词，也不是必须照抄的句子。

在 `qualityContext` 中投影以下脱敏字段：

- `topicSeed`：首轮用于选择具体话题；
- `topicKeywords`：只用于首轮和明确承接样本的证据检查；
- `continuationMode`：`anchored` 或 `pressure`。

后续轮次以最近的真实 `conversation_history` 作为当前话题来源。Prompt 明确要求优先保留上一条 NPC 回复中的一个具体对象、动作或安排；玩家明确点名时，以玩家点名为最高优先级。系统不从模型文本中强行抽取唯一主题，也不把案例种子伪装成已经发生的事实。

### 3. Prompt 行为

首轮 `topic_response_contract`：

- 由 NPC 主动找话题，不回应不存在的玩家句子；
- 先给一个具体、可继续的场景对象，再按关系阶段加入温度；
- 目标案例至少出现偏爱、想念、主动陪伴、调情、靠近或待确认安排中的一种，优先使用角色适合的表达；
- 不用连续天气问句、泛泛「你在干嘛」或任务式汇报代替开场；
- 不把未确认的见面、身体动作或事件写成已经发生。

后续 `chat` 轮的 `continuation_contract`：

- 第一优先级是回答当前玩家输入；
- 至少承接一个最近 NPC 回复或玩家明确提到的具体对象、动作或安排；
- 在承接后新增一个小进展：态度、感受、照顾、调情、具体安排或明确收口；
- 禁止在玩家没有换题时另起无关话题；
- 目标案例需要主动推进亲密关系，但 Shane 等角色可以用嘴硬、照顾和实际行动表达，不强迫其使用统一情话；
- `remote` 只能提出待确认的安排，`face_to_face` 才能描述当面反应，双方同意仍然优先。

连续性契约放在真实历史之后、当前玩家输入之前，避免被角色资料和 few-shot 样例稀释。已有的 `progression_guard`、语气变化卡和关系边界卡继续保留，但不再让 `topic_response_contract` 覆盖后续 `chat` 语义。

### 4. 测试案例

保持 32 例、每例 3 轮和 24 个目标 / 8 个对照的总体规模，但重写后续输入及其评价焦点：

- 目标案例的主要路径使用 `anchored`：第二轮明确提到首轮话题种子或其自然对象，第三轮明确接住 NPC 的安排；
- 每个角色保留少量 `pressure` 案例，第二轮使用「我在听」「你继续说」等短答，要求模型从真实历史中维持话题；
- 不再用同一句「那今晚留一点时间给我们，好吗？」覆盖所有角色；第三轮根据葡萄、音乐、鸡舍、训练、月光等角色话题分别设计自然的确认或安排；
- 目标案例的第一轮重点是具体开场 + 亲密温度，第二轮重点是连续承接 + 主动升温，第三轮重点是确认后的具体安排或自然收束；
- 对照案例同样采用 `topic` 首轮、`chat` 后续，但 `flirtIntensity="none"`，只允许普通日常主动性。

### 5. 评分与诊断

保留 `expected_terms` 作为证据提示，不再把它作为自由开场唯一的通过条件。

新增或明确以下诊断：

- `missing_topic_evidence`：首轮没有触及案例允许的话题种子或场景对象；
- `missing_continuity_evidence`：后续轮没有回应当前输入，也没有保留最近话题的具体锚点；
- `unrelated_topic_shift`：在玩家未换题时引入与当前话题无关的新主题；
- `missing_proactive_affection`：目标轮要求主动亲密，但只有普通天气、工作或泛问句；
- `initiative_boundary_violation`：对照案例越过关系阶段，或远程把待确认安排写成既成事实。

目标案例的单轮通过至少需要：回复非空、无格式噪声、无边界违规、话题证据或连续性证据成立，并满足当前轮的主动性要求。目标案例的整体通过要求 3 轮全部通过；对照案例要求普通话题连续且没有恋爱 / 成人亲密信号。

自动诊断仍然只是筛选信号。每个主要角色至少人工复核一个 `anchored` 目标、一个 `pressure` 目标和一个对照案例，重点检查角色辨识度、真实中文、热情是否像主动意愿，以及是否发生无依据换题。

### 6. 数据流与结果

```text
案例定义
  ├─ 当前轮 intent、topicSeed、continuationMode
  ↓
评测脚本构造 request/context
  ├─ 首轮 topic + 空内部触发
  └─ 后续 chat + 真实玩家输入 + 累积 history
  ↓
PromptBuilder
  ├─ topic_response_contract
  └─ continuation_contract
  ↓
Provider → 回复
  ↓
连续性 / 主动性 / 边界评分
  ↓
独立批次 summary.json + results.jsonl + 网页目录
```

结果只保存脱敏后的案例元数据、回复、评分标签、Provider、延迟和用量；不保存完整 Prompt、Token、Cookie、API key 或内部请求载荷。新批次目录不得覆盖 `20260902-topic-start-intimacy-cloud`。

### 7. 错误处理与回滚

- 案例 intent、关系阶段、成人同意和频道边界在发送 Provider 前校验；失败则不发起云端请求。
- 单轮 Provider 失败只记录当前轮错误，继续其他案例；结果中区分错误、fallback 和正常回复。
- Prompt 契约测试失败时停止云端批次，不使用旧结果冒充新结果。
- 所有实现改动都限制在当前 story-memory 工作树；不操作正式存档、正常 `Mods`、游戏部署目录和现有旧批次。
- 如质量回归恶化，可回退本次实现提交；旧案例和旧工件独立保留。

## 测试计划

1. 先写失败测试，覆盖每轮 intent、空 topic 触发、真实玩家输入保留、话题种子投影、历史承接和新诊断。
2. 运行定向 Python 测试，确认失败原因是行为不符合预期，而不是导入或路径错误。
3. 实现最小请求语义和 Prompt 契约，再运行定向测试。
4. 用 Fake Provider 跑 dating、married、pressure 和 control 小样本，检查 3 轮 history 和结果字段。
5. 运行 Bridge 全量测试、`compileall` 和 `git diff --check`。
6. 重启当前工作树 Bridge，先通过 HTTP 检查实际加载的代码和套件目录，再生成新的独立云端批次。
7. 对新结果做结构化检查和人工抽样；不把自动通过率单独当作角色热情达标证据。

## 验收标准

- 首轮模型请求是 `intent=topic`，消息为空且包含 `topic_response_contract` 与 `topicSeed`。
- 第二、三轮模型请求是 `intent=chat`，保留实际玩家输入，不再发送空 `topic_trigger`。
- 后续回复能承接最近 NPC 话题；无关换题会被诊断为连续性问题。
- dating / married 目标案例缺少主动亲密推进时明确失败，不再被普通 `specific_plan` 误判为热情达标。
- 对照案例不出现恋爱升级或成人亲密信号。
- 新结果批次可被网页选择、独立读取，且不覆盖旧批次。
- 实现前有失败测试，实现后有定向、全量和实际 Bridge 验证证据。
