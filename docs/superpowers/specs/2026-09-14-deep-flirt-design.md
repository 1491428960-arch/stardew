# 深入调情评测套件设计

## 背景

当前 `conversation-lead` 案例主要验证玩家已经给出邀约或亲密暗示后的即时回应。三轮对白虽然完整，但大多数案例在第一轮就进入高关系场景，后续很快回到陪伴安排、工作或普通话题，无法判断 NPC 是否能在玩家明确接住后继续推进一层。

本设计新增独立的 `deep-flirt` 套件，专门观察恋爱或婚后关系中的连续亲密推进。它不修改现有 `conversation-lead`、`affection-pacing` 或历史工件，结果通过已有质量查看器单独读取。

## 目标

1. 为 Wizard、Sophia、Shane、Sebastian、Alex、Elliott、Harvey、Sam 各提供 1 个三轮深入调情案例，共 8 例、24 轮。
2. 在同一案例中覆盖具体话题承接、情绪/语言升温、玩家明确接住后的非露骨身体亲密或尊重收束。
3. 让逐轮输入体现“提出暗示 → 玩家回应或确认 → NPC 再推进/收住”的状态变化，避免把案例级 `adultConsensual=true` 当成每轮自动同意。
4. 保留角色表达锚点、关系阶段、当面渠道和当前场景；每轮最多一个亲密动作，不凭空增加未来排期。
5. 让自动诊断能区分当前话题、个人化亲密、连续性、身体动作边界和角色化收束；自动通过只作为人工复核入口。

## 非目标与边界

- 不加入露骨性行为过程、色情台词、生殖器细节或强迫/非自愿内容。
- `explicit` 只表示已建立关系下的成人亲密语境，不能跳过玩家当前回合的明确回应或同意。
- 8 个新案例使用 `face_to_face`，因为本套件要验证当前发生的靠近、拥抱或亲吻请求；远程“想抱你”等边界继续由现有套件覆盖，不能写成已经发生的身体接触。
- 不新增 `initiativeKind` 枚举；复用 `affection_signal`、`playful_tease`、`companionship`、`guarded_care`、`conversation_exit` 等现有类型。
- 不修改正式 Mods、存档、角色资料库、Bridge/SMAPI 服务或已有质量结果。

## 案例结构

所有案例为 `intent=chat`、`channel=face_to_face`、`romanceEligible=true`、好感度至少 8 心，并按关系阶段设置 `dating` 或 `married`。Shane 使用恋爱阶段和 `direct` 强度；其余角色使用婚后阶段并允许 `explicit` 语境。案例元数据的 `adultConsensual=true` 只代表测试参与者和关系前置条件，逐轮是否继续由玩家输入表达。

三轮固定输入遵循以下结构：

1. 第一轮：玩家从角色专属的共同经历、私密玩笑或暧昧暗示开始。NPC 必须回答当前对象，并落下一处轻度个人化信号，不直接跳到身体动作。
2. 第二轮：玩家明确回应、反撩或确认愿意靠近。NPC 保留上一轮对象，给出一次更直接的情绪回应，并提出或确认一个当前亲密动作；不得堆叠多个动作或引入未来日期。
3. 第三轮：玩家接受、犹豫或要求慢一点。NPC 根据角色接受一个非露骨动作并自然收束，或降低强度、询问状态、尊重拒绝；回复必须能看出它记得前两轮。

角色锚点如下：

- Wizard：克制、古雅、带一点神秘感，把亲密落在共同观察或私下语气中。
- Sophia：温柔、羞涩、俏皮，以葡萄酒、绘画或感官细节承接，但不堆甜腻情话。
- Shane：疲惫、谨慎、带干燥玩笑；第三轮保留“慢一点/先停”的可收束路径。
- Sebastian：少话、别扭，通过音乐、摩托车或安静靠近表达亲密。
- Alex：自信、直接、会夸回和调侃，动作具体但不写成训练或励志演讲。
- Elliott：文学化但落地，用文字、海边或稿件表达偏爱，不把回复写成独白。
- Harvey：温和、谨慎，先确认状态和舒适度，再决定是否靠近。
- Sam：轻快、有行动感、保持成熟，不把亲密写成幼稚玩笑。

## 接线与数据流

`quality_cases_for_suite("deep-flirt")` 返回独立案例元组，`QUALITY_SUITE_IDS` 增加该标识。现有 `scripts/run_character_quality_eval.py --suite deep-flirt` 直接复用评测器、Guard、脱敏结果和批次目录；查看器通过现有 `/api/quality/cases?suite=deep-flirt` 与 `/api/quality/results?suite=deep-flirt` 展示，不创建新的 HTML 或 JavaScript。

## 测试与验收

实现前先补失败回归，覆盖：

- 套件返回 8 例且 ID 稳定、三轮输入完整；
- dating/married、好感、`adultConsensual`、`romanceEligible` 和当面渠道校验；
- 第二轮必须携带上一轮对象，第三轮必须出现接受、降档或收束契约；
- 角色锚点和禁止的未来排期/远程已发生动作不会被案例定义误写；
- Fake Provider 能逐轮把 NPC 回复放入历史，且不产生额外空玩家消息。

离线回归通过后，只生成 `deep-flirt` 前 4 例作为 DeepSeek 小批量观察；工件使用新目录，不覆盖历史结果。最终报告分别给出案例/轮次完成、Provider 错误、重试次数、自动评分和人工自然度判断。
