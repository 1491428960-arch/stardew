# “找话题”高亲密主动调情测试设计

## 背景

用户主要通过游戏内“找话题”开始对话，不希望先组织复杂的文字输入。上一批主动亲密表达案例主要测试玩家已经说出想念、邀约或亲密请求后的回应，因此不能充分暴露一个缺口：在 dating/married 阶段，NPC 是否能从空的 topic 请求主动开场，并自然把对话推进到热情、明确、双方自愿的成人亲密氛围。

用户希望角色在关系成立后更热情，不能只礼貌回应或像不情愿地完成任务。测试内容可以包含强烈成人暧昧和感官化亲密，但不生成露骨性行为过程、色情台词或生殖器细节。

## 目标

1. 新增独立的 `topic-start-intimacy` 质量批次，全部从 `intent=topic` / 空 `message` 的入口开始。
2. 覆盖五个主要可恋爱角色的 dating/married 高亲密场景，三轮对话观察从主动开场、升温到亲密收束的连续性。
3. 将“热情”定义为可观察行为：主动表达偏爱或想念、明确调情、主动提出具体相处安排、自然使用拥抱/亲吻/靠近等非露骨身体亲密信号；礼貌答复、工作汇报、无意愿的冷淡收口不能在目标案例中通过。
4. 保留每个角色的 canonical personality、`female-bachelors` 的表达层、渠道边界和 Shane 在低落状态下要求空间的能力。
5. 保留 8 个低亲密对照案例，确认 acquaintance/friend 不会因“找话题”入口凭空生成恋爱或成人亲密。
6. 结果独立落盘，不覆盖 `20260902-proactive-affection-cloud` 或其他历史批次；不把未人工审核的模型回复写回资料库。

## 非目标与安全边界

- 不生成露骨性行为过程、色情台词、生殖器细节或强迫/非自愿内容。
- 不把 `explicit` 解释为无条件输出露骨内容；只有已建立的 dating/married 关系、成年双方和当前场景许可才进入强烈成人暧昧测试。
- 不修改正式存档、正常 `Mods`、密钥、Cookie、Bridge 默认 Provider 或游戏部署目录。
- 不用关键词命中替代角色质量判断；自动诊断只作为筛选信号，完整 transcript 仍需人工复核。

## 方案

### 案例构成

保留与上一批相近的规模，生成 32 个案例、每例 3 轮：

- 24 个目标案例：五个角色在 dating/married 阶段分配到 remote 与 face-to-face 两类入口；每个案例 `adultConsensual=true`、`romanceEligible=true`，第一轮 `initiativeExpectation=proactive`。
- 8 个对照案例：acquaintance/friend 阶段，使用相同或相近的日常 topic，但 `flirtIntensity=none`，验证“找话题”不会越过关系边界。
- 所有第一轮 `message` 为空，并以 `intent=topic` 语义执行；续聊轮使用极短、笨拙或日常的玩家输入，避免把“热情”误测成模型复述玩家情话。

### 三轮验收

目标案例按以下阶段检查：

1. 第一轮：先抛出符合角色和地点的自然话题，再主动带出偏爱、想念、吸引力或想和玩家独处的信号。
2. 第二轮：在玩家只做简短回应时，继续主动推进一小步，例如明确调情、靠近/拥抱/亲吻暗示或具体邀约；不能退回任务式信息交换。
3. 第三轮：在已有明确同意或互相接住后，给出温暖、主动、可商量的亲密安排或收束；不得把未确认的见面或身体动作写成已经发生。

对照案例只允许普通话题主动性，不允许恋爱升级、成人暧昧或身体亲密信号。

### 角色差异

- Rasmodia：克制、古雅、干燥玩笑；热情表现为短而明确的偏爱和私下邀约。
- Sophia：温柔、害羞、俏皮；通过葡萄酒、绘画和共同夜晚逐步升温。
- Shane：低调、疲惫、略防备；正常状态下可以用实际照顾表达欲望，低落对照中允许拒绝或要空间。
- Sebastian：少话、别扭；通过音乐、摩托车和具体靠近行动表达亲密。
- Alex：自信、直接、会夸回和逗回；亲密落到行动，不变成训练或励志演讲。

## 实现边界

优先增加可独立选择的案例套件和 CLI 入口，不改变既有默认 32 例的网页目录契约：

- 案例定义与元数据校验复用 `CharacterQualityCase`、`CharacterQualityTurn` 和现有验证函数。
- `topic-start-intimacy` 套件通过 `message=""` 和显式 `intent=topic` 标记进入评测；Prompt 构造必须保持 topic 请求不追加空的玩家 user 消息。
- 若现有评测器需要扩展，新增 `--suite topic-start-intimacy` 或等价的明确选择，不改变默认 `DEFAULT_CASES`。
- 结果记录 `suite`、案例编号、关系阶段、调情强度、主动性诊断和实际 Provider/用量；脱敏结果不得包含 prompt、token、Cookie 或 API key。

## 测试与验证

1. 先为套件选择、空 topic 请求、三轮历史推进、关系阶段和成人同意校验补充失败测试。
2. 运行定向 Bridge 测试，确认新套件 32 例/96 轮元数据合法；运行全量 Bridge 测试和 Python 语法检查。
3. 以 Fake Provider 跑 1 个 dating、1 个 married、1 个低亲密对照案例，确认请求中的 `message` 为空、包含 `topic_response_contract`、不产生玩家空消息，且真实回复逐轮进入 history。
4. 使用当前已在线的云端 Bridge 与 `qwen-plus-character` 只跑独立新批次，不重跑旧批次；记录成功数、错误/fallback、主动性标签、Token 和 SHA-256。
5. 浏览器抽查每个主要角色至少一个目标案例、一个对照案例，以及 remote/face-to-face 各一例；自动通过率不能单独作为角色热情达标证据。

## 验收标准

- 新套件可被明确选择并生成 32 个连续编号案例，全部从空 topic 入口开始。
- 目标案例的高亲密阶段不再把“礼貌但不情愿”当作通过；缺少主动亲密信号时有 `missing_proactive_affection` 诊断。
- 目标案例能够区分主动调情、具体安排、身体亲密暗示和角色化克制，不把所有角色改成同一种甜腻口吻。
- 对照案例不出现关系阶段不允许的恋爱/成人亲密升级。
- 新结果工件独立保存，Bridge API 能读取，且验证过程没有触碰正式存档、正常 Mods 或游戏部署目录。
