# 游戏内线上多人对话邀约设计

## 目标

在现有 F8 单 NPC 当面聊天之外，增加一个独立的游戏内线上多人对话入口。玩家按 F9 后可以查看系统根据当前故事状态周期性准备的多人对话邀约，也可以自由选择 2～3 名已认识的 NPC 发起线上群聊。

本规格只覆盖游戏端入口、邀约卡、持久化和与已有 `/api/dialogue/group` 的接线方式。已有 Bridge 的 `fanout`、`turn_based` 和 `multi_turn` 策略不重新设计；游戏端第一版固定使用 `turn_based`。

## 非目标

- 不改变 F8 单 NPC 对话入口。
- 不把附近 NPC 自动识别为多人对话参与者。
- 不在第一版实现线下多人对话。
- 不在后台提前生成完整 AI 台词。
- 不让线上多人对话召唤、传送或移动 NPC。
- 不修改 NPC 日程、库存、正式 Mods、存档文件或角色资料库以外的外部数据。
- 不让邀约直接改变好感度、关系状态或 canonical 故事事实。

## 玩家流程

### 入口分工

```text
F8：当前 NPC 当面聊天
F9：线上多人对话中心
```

`F9` 作为独立配置项 `GroupDialogueKey`，默认绑定 `F9`。配置项为空或无效时回退到默认 F9，不影响现有 `DialogueKey=F8`。

F9 只在世界已加载、没有其他菜单、没有事件/过场、多人会话未进行时处理。触发失败时不关闭现有菜单、不改变玩家位置，也不发起 Bridge 请求。

### 多人对话中心

中心页面包含三个区域：

1. `推荐邀约`：显示未读、未过期和已完成状态的周期性邀约卡；
2. `自由发起`：从已认识 NPC 中选择 2～3 人，自行输入话题；
3. `历史对话`：只显示本地保存的会话摘要和参与者，不要求重新请求云端。

第一版只要求完成前两个区域；历史区域可以先保留空状态和已完成邀约的标题，不保存完整原始 Provider payload。

### 接受邀约

玩家选择邀约后看到确认页：

```text
线上多人邀约
参与者：Abigail、Emily
主题：奇怪的矿石
引导：围绕最近发现的矿石和矿洞传闻展开，不预设 NPC 的最终立场。

[接受并开始] [改为自由聊天] [稍后] [忽略]
```

接受后进入多人输入框。参与者和主题由邀约预填，但玩家仍可以编辑第一条消息；系统不自动播放完整预设对白。

`改为自由聊天` 保留参与者，清除邀约引导，只使用玩家实际输入。`稍后` 保持邀约为未读/待处理，`忽略`将其标记为 dismissed，不再进入默认推荐列表。

## 邀约卡模型

邀约是结构化的本地引导数据，不是 AI 回复。建议新增 `GroupDialogueInvitation` 记录，字段如下：

| 字段 | 含义 | 约束 |
|---|---|---|
| `invitationId` | 稳定 ID | 非空且在当前存档中唯一 |
| `templateId` | 本地场景模板 ID | 只允许内置白名单 |
| `participants` | NPC ID 列表 | 2～3 个；不重复；均为已认识 NPC |
| `title` | 玩家看到的标题 | 来自本地模板，不由模型生成 |
| `topic` | 中性话题摘要 | 不写成 NPC 已经做出的承诺 |
| `guidance` | 给玩家的引导 | 不直接当作 NPC 台词发送给模型 |
| `createdOn` | 创建时游戏日期 | 仅用于本地排序和过期计算 |
| `expiresOn` | 过期游戏日期 | 仅用于 UI 和清理，不代表 NPC 的时间承诺 |
| `source` | 生成来源 | `periodic`、`relationship` 或 `story` |
| `status` | 生命周期状态 | `unread`、`deferred`、`accepted`、`dismissed`、`completed`、`expired` |

`topic` 和 `guidance` 进入 Bridge 时必须作为受控的公开场景上下文，不能替代玩家消息，也不能允许模型把未发生的内容当作 canonical 事实。实际 NPC 回复仍由当前角色资料、公开历史和玩家消息共同生成。

记录可以作为 `StoryStateEnvelope` 的可选列表保存，旧存档缺失该字段时按空列表加载；不升级 schema 版本即可保持向后兼容。序列化前后必须执行参与者数量、NPC 唯一性、日期格式、状态枚举和模板白名单校验。

## 周期性生成规则

第一版采用确定性的本地生成，不在新的一天后台调用云端：

- 每 2 个游戏日最多新增 1 张邀约；
- 未处理邀约最多保留 3 张；
- 默认 7 个游戏日后过期；
- 只有已认识且存在角色资料的 NPC 才能进入邀约；
- 同一 `templateId + participants` 组合在最近 7 个游戏日内不重复；
- 当前存在多人会话、事件或特殊过场时，只延后生成，不弹出菜单；
- 新的一天只显示轻量提示或 F9 徽标，不自动打开对话；
- 关系修复、线上线下承接等特殊状态可以生成 `relationship` 或 `story` 来源邀约，但仍必须经过同一数量和过期限制。

候选模板根据当前状态筛选：季节/天气、最近分享或展示过的物品、近期公开记忆、关系阶段、开放循环和玩家最近对话主题。筛选结果必须是角色身份和既有故事事实允许的组合；没有合适候选时不生成邀约。

邀约生成器只选择模板和参与者，不撰写 NPC 的具体台词。这样可以在云端不可用时继续展示引导，也避免为未接受的邀约消耗额度。

## 游戏端数据流

```text
新的一天事件
  -> GroupInvitationGenerator
  -> GroupInvitationStore
  -> F9 中心读取未处理邀约
  -> 玩家接受邀约
  -> GroupConversationSession
  -> BridgeClient POST /api/dialogue/group
  -> turn_based 回复
  -> 游戏内按 speakerNpcId 分段显示
  -> 成功结束后标记 completed
```

Bridge 请求固定满足：

- `channel=remote`；
- `strategy=turn_based`；
- 参与者为邀约中的 2～3 名 NPC；
- 当前发言人由游戏端按服务端返回轮次处理，不由模型自由添加；
- 公开历史只包含本次群聊成功生成的内容；
- 不发送 API Key、Authorization、完整本地存档或无关隐私数据。

游戏端展示每条回复时必须使用返回的 `speakerNpcId` 查找参与者头像和显示名。未知发言人、空回复、HTTP 错误、超时、`fallback=true` 或响应结构不完整时，当前轮标记失败，不把邀约标记为 completed，也不把失败文本写入公开历史。

## 线上边界与角色安全

- 线上邀约不要求 NPC 在当前地图或当前时间段可见；不创建实体 NPC。
- NPC 只能代表自己发言，不能代替名单外 NPC 说话。
- 引导不允许包含未来日期、预约、排期、固定陪伴时间或改变 NPC 日程的承诺。
- 关系、嫉妒、修复和亲密话题只作为公开上下文约束，不由邀约卡直接宣布结果。
- 参与者选择必须保留 canonical `npcId`；显示名、性别表达和代词仍由角色资料层决定。
- 第一版不区分普通玩家群聊和特殊角色群聊的额外权限；角色是否可聊天仍沿用现有资料索引和目标过滤规则。

## 实现组件边界

实现阶段按以下职责拆分，不把所有逻辑塞进 `ModEntry`：

- `ModConfig`：新增并规范化 `GroupDialogueKey`。
- `GroupInvitationModels`：邀约记录、状态和模板输入输出模型。
- `GroupInvitationGenerator`：按游戏日期和公开故事状态产生候选邀约，不执行网络请求。
- `GroupInvitationStore`：在现有故事状态容器中校验、读取、更新和清理邀约。
- `GroupParticipantMenu`：F9 后选择邀约或自由发起参与者。
- `GroupConversationMenu` / `GroupConversationSession`：输入、轮次、回复展示和中断处理。
- `BridgeClient`：新增多人请求/响应协议，复用现有 loopback endpoint、超时和诊断日志边界。
- `ModEntry`：只负责按键入口、游戏事件转发和菜单生命周期。

## 测试与验收

实现必须先按 TDD 编写失败测试，再写最小实现。至少覆盖：

1. 默认 F9、生效配置、无效配置回退和 F8 不受影响；
2. 每 2 个游戏日最多一张、最多 3 张待处理、7 日过期和重复模板去重；
3. 只允许 2～3 名已认识且有资料的唯一 NPC；
4. 旧故事状态 JSON 缺少邀约字段时正常加载，非法邀约被拒绝或跳过并留下可诊断警告；
5. F9 在菜单、事件和多人会话期间不打断游戏；
6. 接受、稍后、忽略、完成和失败重试的状态转移；
7. Bridge 请求固定为 `remote + turn_based`，并正确处理空回复、未知 speaker、fallback、超时和 HTTP 错误；
8. 失败回复不污染历史，失败邀约不被标记为 completed；
9. 线上邀约不要求 NPC 在场，不创建或移动 NPC，不写入日程承诺；
10. C# 单元测试、Bridge 相关定向测试、Bridge 全量测试、`compileall` 和 `git diff --check`。

验收标准是：玩家可以在不启动 Stardew/SMAPI 的单元测试中完整走通邀约生命周期和多人请求契约；真实游戏接入仍需在后续隔离测试存档中单独确认，不把 C# 构建或 `/health` 当作游戏内功能已验证。

## 当前明确取舍

第一版选择“F9 独立入口 + 本地周期性邀约卡 + 接受后实时生成对白”。不采用自动检测附近 NPC，不采用后台预生成完整对白，也不把邀约逻辑并入 F8。这样可以保持单人聊天兼容，控制云端消耗，并为未来的线下多人对话复用参与者、会话和邀约模型。
