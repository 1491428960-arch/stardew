# NPC 剧情、常态记忆与关系阶段设计规格

## 1. 目标与范围

本规格定义 AI NPC 的长期状态层，覆盖原版与 Stardew Valley Expanded（SVE）NPC，并兼容 Romanceable Rasmodia 和男性可恋爱角色娘化内容包。

第一版要让 NPC 能够记住重要经历、理解原版剧情进度、根据原版心级表现出阶段差异，并在聊天中引用玩家确实经历过的事件。它只增加 AI 对话层和持久化状态，不替换原版剧情，也不接管 NPC 日程。

### 1.1 事实优先级

事实源按以下顺序解释：

1. 原版游戏状态：心级、礼物、事件标记、婚姻、孩子和任务结果。
2. 已加载 Mod 的明确剧情：SVE、Rasmodia 等内容包的事件、对白和条件。
3. 游戏运行时观察：NPC 当前地点、活动、天气、季节和时间。
4. 玩家聊天与 NPC-NPC 小事件：只能产生带来源和置信度的记忆，不得凭空修改世界事实。

原版心级和已完成的原版/Mod 事件是关系阶段的主导依据。AI 不能直接把聊天结果变成大幅心级变化，也不能越过尚未满足的剧情条件。

### 1.2 非目标

- 不修改 NPC 的移动路线、日程和寻路。
- 不自动创造新的恋爱关系、仇恨关系、家庭关系或主线事件。
- 不拦截或重写原版每日对白、节日对白和过场事件。
- 不把全部历史聊天永久保存为原文。
- 手机入口不提供背包物品展示；物品互动只在面对面入口处理。

## 2. 核心数据模型

所有模型都使用稳定的内部 NPC ID。显示名、性别、代词和称谓属于 AI 语义覆盖，不改变游戏内部 ID。

### 2.1 `NpcProfile`

描述 NPC 的静态身份、说话风格和阶段行为。

| 字段 | 说明 |
| --- | --- |
| `npcId` | 游戏内部 ID，必填且稳定 |
| `displayName` | AI 对话中使用的显示名 |
| `identityOverlay` | 性别、代词、称谓、别名和生效条件 |
| `sourceMods` | 提供或覆盖该资料的 Mod ID |
| `coreTraits` | 性格、价值观和长期动机 |
| `voiceStyle` | 句式、语气、常用词、禁用表达和情绪范围 |
| `stageProfiles` | 每个关系阶段的称呼、开放程度、话题池、边界和物品反应 |
| `knowledgeRules` | 该 NPC 可以知道、不能知道和需要保密的内容 |
| `activeWhen` | Mod、配置或事件条件；未满足时不启用覆盖 |

娘化贴图包只有 `EditImage` 时，`identityOverlay` 仍由本项目提供。已知的 Sabrina、Elena、Harriet 等明确别名写入覆盖配置；没有明确别名的角色保留原显示名，但使用女性性别和代词，不猜测新名字。

### 2.2 `StoryEvent`

描述一个可验证的剧情事实，不等同于 NPC 的个人记忆。

| 字段 | 说明 |
| --- | --- |
| `eventId` | 稳定事件 ID，包含来源 Mod 和原始键 |
| `sourceMod` | `vanilla`、`SVE`、`Romanceable Rasmodia` 或其他来源 |
| `sourceKind` | 事件、邮件、任务、婚姻、孩子、节日或关系标记 |
| `sourceKey` | 原始数据键、事件键或事件标记 |
| `participants` | 事件涉及的 NPC 和玩家 |
| `conditions` | 触发所需的心级、旗标、季节或 Mod 条件 |
| `status` | `unknown`、`available`、`completed`、`unavailable` |
| `gameDate` | 游戏内日期；未知时为空 |
| `canonical` | 是否为来源 Mod 明确声明的事实 |
| `summary` | 脱离原文后的短事实摘要 |
| `evidence` | 可追溯到的文件路径、键和运行时旗标 |

静态资料索引器只建立候选事件；只有游戏运行时观察到对应旗标或事件完成状态后，才把事件标记为 `completed`。

### 2.3 `MemoryRecord`

描述某个 NPC 对一件事的个人记忆。每条记忆必须包含来源、置信度、时间、参与者和知识范围。

| 字段 | 说明 |
| --- | --- |
| `memoryId` | 唯一 ID，保证重复写入可去重 |
| `ownerNpcId` | 这条记忆属于谁 |
| `kind` | `fact`、`impression`、`promise`、`preference`、`socialEvent` |
| `content` | 面向模型的短摘要，不保存完整聊天 |
| `source` | `vanillaEvent`、`modEvent`、`gift`、`scheduleObservation`、`playerChat`、`npcNpcEvent` 或 `systemInference` |
| `confidence` | 0～1 的置信度 |
| `gameDate` | 发生或被记住的游戏日期 |
| `participants` | 事件参与者列表 |
| `knowledgeScope` | `private`、`participants`、`npcGroup`、`public` 或 `playerOnly` |
| `knownBy` | 已明确知道该内容的 NPC 列表；公开信息也必须显式记录 |
| `importance` | 0～3，决定保留和检索优先级 |
| `canonical` | 是否来自已确认的原版或 Mod 事实 |
| `expiresOn` | 可选的过期日期；普通闲聊允许遗忘 |
| `status` | `active`、`corrected`、`superseded`、`forgotten` |
| `evidence` | 来源文件、事件标记、聊天会话或日结事件 ID |

重要剧情、承诺、婚姻、孩子和重大冲突使用高 `importance`，不自动过期。普通寒暄和低价值 NPC-NPC 小事只保留摘要，并按时间衰减。出现矛盾时不覆盖原记录，而是建立 `corrected` 或 `superseded` 记录，保留可追溯关系。

### 2.4 `KnowledgeRecord`

`KnowledgeRecord` 是 `StoryEvent` 到 NPC 的知识投影，用于防止全知视角。

- 每个参与 NPC 拥有独立投影。
- NPC 只读自己知道的 `MemoryRecord` 和允许公开的 `StoryEvent`。
- 玩家告诉 NPC 的内容默认进入 `playerOnly` 或该 NPC 私有范围，不自动扩散。
- NPC-NPC gossip 只能沿关系边传播低敏感信息，并降低置信度；秘密、恋爱和冲突不得自动扩散。

### 2.5 `RelationshipEdge`

NPC-NPC 关系使用有向图边表示，玩家与 NPC 的关系也使用同一结构。

| 字段 | 说明 |
| --- | --- |
| `fromNpcId`、`toNpcId` | 关系双方；玩家使用固定 `player` ID |
| `relationType` | 家人、朋友、同事、竞争、恋爱或其他已确认类型 |
| `strength` | 关系强度 |
| `tension` | 当前紧张度 |
| `source` | 原版、SVE、Mod 事件、运行时事件或玩家互动 |
| `canonical` | 是否为来源资料确认的关系 |
| `visibility` | 谁可以知道这条关系 |
| `updatedOn` | 最近一次确定变化的游戏日期 |

静态关系和已确认剧情关系优先。AI 只能在规则允许的范围内调整 `strength` 与 `tension`，不能直接创建新的恋爱或敌对边。

### 2.6 `RoutineSnapshot`

这是只读的当前状态，不是日程修改接口。

字段包括游戏日期、季节、天气、时间、地点、当前活动、下一个可靠的日程节点、来源和置信度。读取失败时只省略该字段，不阻断聊天，也不猜测 NPC 位置。

### 2.7 `DialogueSample`

对白资料分成两类：

- **风格证据：** NPC 的原句、说话场景、关系阶段、情绪和语气，用于模仿表达。
- **剧情事实：** NPC 明确陈述的经历、关系和事件，转成 `StoryEvent` 或 `MemoryRecord`，不依赖模型自行推断。

运行时只检索当前阶段和话题相关的 3～8 条样本，不把整个 `i18n/zh.json` 放进 Prompt。

## 3. 关系阶段与有效互动

原版心级定义基础阶段，重大原版旗标可以覆盖普通心级判断：

`初识 → 熟悉 → 朋友 → 亲近 → 恋爱 → 订婚/结婚 → 婚后 → 育儿`

不可恋爱 NPC 使用平行阶段：

`初识 → 熟悉 → 朋友 → 信任 → 挚友 → 家人般关系`

每个 NPC 的 `stageProfiles` 提前配置阶段表现，包括称呼、主动找话题的频率、敏感话题边界、秘密开放程度、物品反应和冲突恢复方式。

### 3.1 有效互动定义

一次有效互动是完整的、有来回的 AI 会话，满足以下条件：

- 玩家发送至少一条非空、非重复的内容。
- NPC 成功返回与当前上下文相关的回复。
- 没有使用 fallback、错误模板或纯技术提示完成会话。
- 同一 NPC 每个游戏日最多计入 1 次有效互动。

默认每次阶段转换需要 4 次有效互动；恋爱、结婚和育儿等重大阶段默认需要 5 次。NPC 配置可以提高门槛，但不能绕过原版事件条件。

### 3.2 好感度变化

原版礼物、普通交谈、事件和婚姻流程继续使用原版规则。AI 会话只产生一个待裁决的关系信号，由本地规则引擎决定是否应用：

- 单次 AI 会话默认最多改变 10 点原版 friendship points。
- 同一 NPC 每日 AI 变化默认不超过 20 点。
- 阶段未满足有效互动门槛时，关系信号只更新记忆、信任或紧张度，不推进阶段。
- 重大原版事件和礼物结果优先于 AI 信号；AI 不回滚原版结果。

所有数值均通过版本化配置管理，不能由模型直接返回最终数值。

## 4. 事件、记忆和关系的数据流

### 4.1 静态索引

离线索引器读取已安装 Mod 的 `manifest.json`、`i18n/zh.json`、Content Patcher `content.json`、对白、日程和事件资产，生成派生索引。原始 Mod 文件不复制进代码仓库，也不在运行时全量读取。

索引器需要保留来源 Mod、原始文件、数据键、翻译文本、角色 ID、阶段和条件，才能在发现冲突时回溯。

### 4.2 游戏内采集

游戏侧按以下时机采集：

1. 进入世界或切换日期：读取心级、婚姻、孩子、事件旗标、任务结果和当前日程快照。
2. 原版事件结束：写入已完成的 `StoryEvent`，再投影给参与者。
3. 送礼、分享食物或有效 AI 会话结束：产生关系信号和对应记忆。
4. 日结前：保存 NPC 位置和活动快照，供下一天生成小型 NPC-NPC 事件。

### 4.3 NPC-NPC 日结事件

第一版每天只生成 1～3 个低影响小事件。候选由日程重叠、地点重叠、静态关系和当天已确认事件决定；本地规则先判断事件类型，AI 只负责需要自然语言的描述。

事件使用 `saveId + gameDate + 固定 seed` 生成幂等键。日结时捕获，下一天开始时落盘，避免保存过程被模型请求阻塞。每个参与者获得独立视角和知识范围，玩家只能通过后续 NPC 聊天逐渐发现，不显示全局新闻日志。

## 5. 持久化与兼容

使用 SMAPI 的存档数据接口保存版本化状态包：

```text
stardew-ai-npc/story-state/v1
```

状态包包含 schema 版本、NPC 记忆、关系边、已确认事件、日结事件幂等键和最近一次索引版本。读取旧版本时执行显式迁移；数据损坏或字段不完整时只丢弃无法解析的记录，保留原版游戏继续运行，并写入一次可诊断日志。

新 Mod 未安装时，相关 `sourceMod` 数据不加载，不删除已有记忆。Mod 重新安装后按来源和事件 ID 恢复可识别内容。

## 6. Bridge 上下文边界

Bridge 每次请求只接收：

- 当前 NPC 的身份和阶段资料。
- 原版心级、婚姻和事件状态摘要。
- 当前地点、时间、天气和日程快照。
- 与当前话题相关的记忆摘要和 3～8 条风格样本。
- 明确允许该 NPC 知道的 NPC-NPC 事件。

Bridge 返回的内容只能包括回复文本、可选的关系信号、可选的记忆候选和引用的上下文 ID。关系数值、记忆来源、知识范围和是否写入存档都由本地规则引擎裁决。

## 7. 测试与验收

### 7.1 数据与索引测试

- Vanilla、SVE、Rasmodia 和娘化覆盖可以合并为稳定的 `NpcProfile`。
- SVE 的中文对白、事件和日程索引保留来源键，不混淆风格证据和剧情事实。
- 缺失翻译、缺失 Mod 或未知 NPC 时只跳过对应项。

### 7.2 规则测试

- 原版心级和婚姻事件覆盖 AI 阶段推断。
- 3 次无效聊天不会计入有效互动；重复消息不能推进阶段。
- 默认 4 次有效互动才能推进普通阶段，重大阶段默认 5 次。
- 单次和每日 friendship points 上限生效，模型不能绕过上限。
- 记忆始终包含来源、置信度、时间、参与者和知识范围。
- 玩家私聊不会自动出现在其他 NPC 的记忆中。
- 旧记忆被纠正时保留原记录和证据链。

### 7.3 日结与持久化测试

- 同一存档、日期和 seed 重复加载不会生成重复 NPC-NPC 事件。
- 每个 NPC 只看到自己的知识投影。
- 存档写入、读取、迁移和损坏记录都不会阻断原版游戏。

### 7.4 代表性夹具

自动化夹具至少包含 Wizard、Sophia、Shane 娘化版和 Rasmodia，覆盖原版、SVE、贴图娘化、双内部 ID 和婚姻阶段。全员资料扩展不改变这些契约。

## 8. 分阶段实施顺序

1. 建立上述模型和版本化序列化测试。
2. 实现离线资料索引器和 Vanilla + SVE 全员骨架。
3. 接入原版事件、好感、婚姻、孩子和日程快照。
4. 实现记忆投影、知识范围和阶段门槛规则。
5. 实现 NPC-NPC 日结小事件与有限 gossip。
6. 将统一上下文接回面对面 `DialogueBox` 和 Smartphone 入口。
7. 运行 Bridge、SMAPI 和代表性存档回归，再扩充人物细节。
