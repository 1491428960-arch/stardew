# 约束作用域台账

> **目的**：让「两条约束是否冲突」可以**机械判定**，不必每次靠读句子猜。
> **起因**：2026-09-28 一晚之内我四次把「作用域不同」误判成「矛盾」，四次都错
> （见 `docs/STATE.md` §三）。根因是**只读句子内容，不读它的作用域**。
> **服务对象**：改 prompt 的 agent，以及 `scripts/check_prompt_consistency.py`。
> 最后更新：2026-09-28 05:45　（**状态：样板已完成，尚未铺开**）

## 一、判定规则（四条，必须同时成立才算冲突）

两条约束**冲突**，当且仅当：

1. **管同一个量** —— `quantity` 相同；
2. **生效条件重叠** —— `condition` 有交集；
3. **取值方向相反** —— 不是「一条更严」，而是互相抵消；
4. **优先级相同** —— `priority` 相同。

任一条不成立 ⇒ **不是冲突**。

**关键**：「取值更严的那条覆盖更松的」是**正常分级**（阶段边界、条件特化都靠它），
**不是矛盾**。今晚四次误判全部栽在这一条上。

`priority` 取值：`default` < `override`（阶段卡、条件特化卡用它提高优先级）。

## 二、样板：`length_whole_reply`（整条回复的长度）

选它做样板，是因为它是**唯一确认过的真冲突**，而且已经修完 —— 用它验证判定规则能否
复现已知答案。

| # | 卡 | 原文（节选） | quantity | condition | priority | 取值 |
|---|---|---|---|---|---|---|
| 1 | `safety_rules` | 中文通常 1–2 句、15–40 字 | `length_whole_reply` | `always` | `default` | 1–2 句 / 15–40 字 |
| 2 | `safety_rules` | …玩家那句话只是由头，只保留一个平实事实或感受，最多两句 | `length_whole_reply` | `input ∈ {寒暄, 近况}` | `default` | ≤ 2 句 |
| 3 | `stage_execution_card` | 回复最多 1 句，只有问题确实需要时才补第 2 句 | `length_whole_reply` | `stage == stranger` | **`override`** | ≤ 1 句（必要时 2） |
| 4 | `voice_execution_card` | 一句话通常十来个字，最多二十出头 | **`length_per_sentence`** | `always` | `default` | 每句 ≤ 20 字 |

**按四条规则判定：**

- #1 与 #2：同量、条件重叠，但 **#2 是 #1 的子集且更严** ⇒ 分级，**不冲突**；
- #1 与 #3：同量、条件重叠，但 **#3 优先级更高且更严** ⇒ 覆盖，**不冲突**；
- #1 与 #4：**不是同一个量**（整条 vs 每句）⇒ **不冲突**；
  而且 `2 × 20 = 40`，与 #1 的 15–40 字**正好吻合**。

⇒ **这个量上没有冲突** —— 与 2026-09-28 的实测结论一致，**判定规则复现了已知答案**。

### ⚠ 修的是什么（此量曾经的真冲突）

收束前，同一轮 prompt 里存在 **`1–2 句` / `1–3 句` / `2–3 句` 三种取值**，
**同量、条件同为 always、优先级同为 default、取值方向相反** ⇒ 四条全中 ⇒ **真冲突**。
模型取了最宽的那条（实测平均 70.5 字）——收束到统一取值后降到 38.8 字
（云端对照见归档报告 §15）。

## 四、为什么用台账而不是继续读句子

| 读句子（现状） | 查台账（目标） |
|---|---|
| 每次都要判断「这算不算矛盾」 | 同一张表，同一套规则 |
| 判断随当轮上下文漂移 | 判定可复现 |
| 我四次都错 | 错也只会错在**建表**那一刻，且能被反向校验抓住 |
| 结论散在报告各处 | 单一落点 |

⚠ **建表本身就是判断**，所以 §一 的规则要尽量窄 —— **宁可漏判，不可误判**：
漏判的代价是「一处冲突没发现」，误判的代价是「删掉一层有意的防御」（今晚差点发生）。

## 抽取器盲区修正（2026-09-28 早）

### 发现
`scripts/check_prompt_consistency.py` 从真实 prompt 抽出量约束，是台账的**唯一数据源**。
用独立宽口径正则复核（`.tmp/length-probe/probe_extraction_blindspot.py`）：

| | 修正前 | 修正后 |
|---|---|---|
| 含数量片段 | 90 | 90 |
| 抽取器抓到 | **24（27%）** | **62（69%）** | **58（64%）** |
| —— 说明 | 太窄，只认少数写法 | 放宽后 | 2026-09-28 晚**收紧**：排除「同一句」「紧接的一句」「复述一句」等指示词/动作短语 ⇒ **降的全是假阳性**，真约束一条没丢 |
| 因 >120 字被跳过 | 11 | **0** |

**⇒ 此前 `--against-scope` 报「0 缺口」不是因为台账完整，而是因为抽取器漏了。**

两个结构性原因：
1. `_MAX_FRAGMENT = 120` —— `stage_execution_card` 的 JSON 片段常在 128–156 字、
   `persona_core` 达 225 字，**最该查的卡片被直接排除**。已提到 300。
2. 正则一律要求「最多/只」或「N–N」形态，而 prompt 里大量约束是**无限定词**写法：
   「**用 1 句**直接回答」「再补**第 2 句**」「断成**第二句**」「提出**一个**具体下一步」。

### 修正后新暴露的量约束（已补进台账）
| 卡 | 量 | 值 |
|---|---|---|
| `persona_core` | followup_count | 「再反问一句」（招牌动作） |
| `persona_core` / `voice_execution_card` | length_per_sentence | 「十来个字，最多二十出头」 |
| `post_history_voice_guard` | action_count | 「一个角色化细节或态度」 |
| `story_state` | action_count | 「一个具体下一步」 |
| `voice_execution_card` | particle_frequency | 「一组三轮最多一次」（**新量**） |

补完后缺口重新清零 —— 这次是在 **69% 覆盖**下清零的，比之前的 27% 可信得多。

两处踩坑记录：
- 「十来个字」会**先被「字数」正则命中** ⇒ `CARD_QUANTITY_OVERRIDES` 的句数侧与字数侧都要改，
  只改一侧会留下「persona_core × length_whole_reply」这个**假缺口**。
- 同一句原文可能**同时出现在两张卡**（`persona_core` 与 `voice_execution_card`）⇒ 两张卡都要记，
  否则报缺口。

### 台账边界（明确写下，避免反复纠结）
**只纳入「上限 / 下限」类的数值约束。** 指代（「任何一个」「这一项」）、
描述（「一个人或一样东西」）、方式（「换一种起句」）都**不算**，即使命中正则。
剩余 31% 未抽取片段经逐条人工判断全部属后三类，另加一条「保留一个必要对象词」
（是「必须包含」而非「至多」），按边界不纳入。

## 范围盲区与取值归一化（2026-09-28 早，续）

### 新工具：persona 静态扫描
`.tmp/length-probe/probe_persona_static_conflicts.py` —— 直接读
`data/personas/*.json` 的 `sentencePattern` / `responseRules` / `signatureMoves`，
找**同一个 voiceStyle 内**的「同量多值」。

**为什么需要**：`check_prompt_consistency.py` 只扫**实际进 prompt 的卡**，
所以**未启用配置里的冲突扫不到** —— `rasmodia.json` 那处（`1–3 句` vs `1–2 句`）
就是靠人工读出来的。这把范围补上了。

**扫 50 个 persona 定义，6 组「同量多值」，经查全为合法多值**（2026-09-28 晚更正：
此前记为「4 组」，是**读错了工具输出的措辞** —— 它写的是「同量多值」而非「取值多于一种」，
锚错字符串 ⇒ 一直报 0 组）：
- `sentencePattern` 与 `responseRules` 管**不同粒度**（句式节奏 vs 场景长度）；
- 「断成第二句」是**断句行为**，「就一句」是**片段长度**；
- 「用一两句」是**整条**，「补一句」是**片段**。

⇒ 工具**只摊开取值、不判冲突**（与原工具一致），退出码恒为 0。

### 踩坑一：取值不能提取「匹配到的文本」，必须归一到数值
放宽正则后，静态扫描一度报出 **20 处假冲突**，根因是：

> 同一段话里「**用一句**」与「**一句**」是两个不同 match，但说的是**同一个取值 1**。

同理「再补一句」/「补一句」/「一句」。新增
`check_prompt_consistency.normalize_value()` 把取值归一成 `1 句` / `15–40 字` 这类
**数值 + 单位**。修后 20 → 4，且 `--stage` 输出从「用一句 / 一句混排」变成可读的 `1 句` / `2 句`。

**连带修**：`补` 必须后接**「第」**才算长度约束 ——
「再补**第** 2 句」在定上限，而「补一句自我怀疑」是**动作**。

### 踩坑二：改了取值口径，所有消费者都要跟着改
归一化引入一处**假性失配**：盲区探针用 `v in frag` 比较，
而抽取器返回 `10 字`、原文是 `十来个字` ⇒ 覆盖率一度从 **69% 掉到 16%**。
两侧都归一化后才恢复。**改一处口径就要盘所有下游**。

### ⚠ 更正（同日）：上面「rasmodia.json 句数取值冲突」的判断**是错的，已回滚**

判据用了「同量 / 同卡 / 同优先级 / 条件重叠」，但漏了一步：**读粒度**。

- `sentencePattern`：「用 1–3 句短句**收束**」⇒ 管**句式节奏**（怎么收尾）
- `responseRules`：「**日常寒暄**通常只说 1–2 句」⇒ 管**一个具体场景**（比前者更严）

**不同粒度、方向一致 ⇒ 这是分层防御，不是冲突。**

**决定性证据**：`bridge/tests/test_prompts.py::test_rasmodia_voice_style_captures_source_rhythm_and_register`
的 `assert "1–3 句" in sentence_patterns` 钉住了这个值。改完数据后全量立刻
`1 failed, 4313 passed`。**已从备份回滚，测试恢复通过。**

⇒ 这是同源误判的第 **6** 次（前 5 次见 `docs/STATE.md` §三）。新增可执行检查顺序：
**改任何「看起来矛盾」的值之前，先 `grep` 它有没有被测试断言 —— 有就先假设它是有意设计。**

（本节的教训比结论重要：**静态扫描器报出「同量多值」时，多值本身不是判决**，
它只是把需要人看的地方摊开。真冲突与分层防御在「取值」这一层长得一模一样，
区别只在**粒度**与**测试是否钉住**。）

### ⚠ 抽取器已知的三类假阳性（2026-09-28 修正）

裸 `N 句` 会把下面这些**当成句数上限**：

| 命中文本 | 实际性质 |
|---|---|
| 「同**一句**」「紧接的**一句**」 | **指示词** —— 说的是位置，不是句数 |
| 「复述**一句**→回答**一句**」 | **动作描述** —— 说的是两个动作 |
| 「不要在**同一句**中重复名词」 | 同上 |

修正：fallback 加 `(?<!同)(?<!的)(?<![复述答说讲读写问聊谈提及])`。
代价是覆盖率 **69% → 64%**，已核对**降的全是假阳性**；
真约束（「补第 2 句」「最多两句」）由前置专门规则接住。

⚠ **教训**：抽取端放宽会同时放进真约束和假阳性，收紧又要防误伤 ——
每次调整都必须**同时**跑 `probe_extraction_blindspot.py` 看覆盖率、
并**人工核对漏掉的样本**，不能只看数字。

# ⭐ 台账的完整性声明：六类盲区（2026-09-28 晚汇总）

**为什么单列一节**：这六类盲区**性质完全不同**（抽取、数据结构、评测集、
评测集内部的话题对齐、验证工具、**prompt 组装**），但后果一样 ——
**都是台账「看不见」的地方**。
混在一起谈会互相掩盖，所以列成一张表，并写清**每类各自怎么发现、怎么应对**。

### ⭐ 前三类问「查得到吗」，第四类问「**工具可信吗**」，第五、六类问「**问对了吗 / 到得了吗**」

| 类 | 它回答的问题 |
|---|---|
| ①② | 约束**被登记 / 被表达**了吗 |
| ③ | 该**阶段**有样本吗 |
| ④ | 我的探针**真的在变输入、真的没误报**吗 |
| ⑤ | 该阶段有样本，但**样本问的是那件事吗** |
| **⑥** | 规则写进了数据，但**它到得了 prompt 吗** |

| # | 盲区 | 性质 | 现状 | 应对 |
|---|---|---|---|---|
| 1 | **抽取端漏抓** | 正则覆盖不全 | 覆盖率 **64%**（58/90），漏 28 条 | 已知且**已核对**：漏的全是假阳性类（指代/描述/方式） |
| 2 | **跨量算术** | **数据结构层面** | 台账按 `quantity` 分桶 ⇒ **跨量的算术关系结构上不可见** | `probe_cross_quantity.py`，21 组合查出 8 对，**真 1 对** |
| 3 | **评测集阶段没覆盖** | **样本层面** | 全部 suite 并集 **255 个 case** 里 **stranger / parent 各 0 个**；acquaintance 有 12 个但只跑了 4 个 | `probe_untestable_scope.py` |
| 4 | **验证工具自身失效** | **工具层面** | 探针曾因参数名错**静默全错**；也曾因**名字编码不一致**误报 | 不变量自检（不同输入须产生不同输出） |
| 5 | **阶段对了话题不对** | **样本 × 话题层面** | acquaintance 有 **12** 个 case，但**一个邀约场景都没有** ⇒「初识不得邀约」**跑全也测不到** | `probe_topic_alignment.py` |
| 6 | **写进数据到不了 prompt** | **prompt 组装层面** | 角色 `responseRules` **到达率只有 50%**（写 4 条进 2 条）⇒ 台账**看不见**，因为它只扫 prompt 文本 | `probe_response_rules_reach.py` |

## 逐类说明

### ① 抽取端漏抓（已知，边界已划定）

**只纳入「上限 / 下限」类的数值约束。** 指代（「任何一个」）、描述（「一个人或一样东西」）、
方式（「换一种起句」）**不算**，即使命中正则。剩余 31% 未抽取片段经逐条人工判断
全部属后三类 ⇒ **漏的是噪声，不是真约束**。

⇒ 所以这一类**当前是可接受的**，但必须记住：
**覆盖率是「已抽取的确定性」，不是「不存在的证明」。**

### ② 跨量算术（结构上不可见）

台账的键是 `quantity`，冲突判定要求 **`quantity` 相同** ⇒
**「句数写 2 句」和「字数写 40 字」之间的关系，台账结构上就表达不了。**

而实测**恰好存在这样一对真冲突**：`1–2 句、15–40 字` ——
按每句中位 **18 字**算，2 句自然落在 36~40 字，**两个上限同时卡在边界**。

⇒ 这是**今晚核心结论的由来**（见 `docs/STATE.md` §二）。
⇒ 工具：`scripts/probe_cross_quantity.py`（零请求）。

### ③ 评测集没覆盖（本轮新发现，**最根本**）

⚠ **这里我错了两次，都记下来**（都是「代理指标代替真对象」的同一形状）：

1. **查错源头**：以为「可跑的 case」在
   `data/personas/behavior-quality-scenarios.json` —— **错**。
   那是**本地行为样本生成器**（`generate_behavior_examples.py`，
   `--provider` 只有 `local`）的输入，**与云端评测无关**。
2. **只看 default**：以为看 `DEFAULT_CASES`（47 个）就够 —— **错**。
   artifact 里 married 跑过 **59** 个，**比 default 还多** ⇒ case 来自**多个 suite**。

**正确口径**：云端 case 定义在源码
`bridge/src/stardew_ai_bridge/character_quality_eval.py` 的 `_BASE_CASES`，
**「可跑的」= 全部 suite 的并集 = 255 个 case**。

| 阶段 | **跑过的**（artifact） | **并集里的**（可跑） | 结论 |
|---|---|---|---|
| **stranger** | **0** | **0** | ⚠⚠ **两边都空** ⇒ 要**加 case** |
| **parent** | **0** | **0** | ⚠⚠ **两边都空** ⇒ 要**加 case** |
| acquaintance | 4 | **12** | ⚠ 跑全**也未必够** |
| close | 9 | 20 | ⚠ 跑全**也未必够** |
| friend | 22 | 44 | ⚠ 跑全**也未必够** |
| dating | 36 | 55 | ⚠ 跑全**也未必够** |
| married | 59 | 124 | ⚠ 跑全**也未必够** |

（artifact 共 **213** 个不同 caseId。）

**两个后果**：

1. **限定在「初识」（= `stranger`）阶段的约束，用现有 artifact 完全测不了** ——
   该阶段**一个 case 都没有**。
   ⚠ **注意口径**：台账（结构化 28 条）里带阶段限定的只有 **3 条**，
   其中 **2 条**是 `invite-action` / `followup-stranger`，
   `cond` 都是 **`stage: stranger`**；
   而按**片段**扫是 **9 条**（涉及 2 张卡）。**两个口径不同，别混用。**
   ⚠⚠ **「初识」= `stranger`，不是 `acquaintance`**（实测：那条约束只出现在
   `stranger` 的 `stage_execution_card` 里）。我一开始映射错，
   于是把原因说成了「acquaintance 样本少」—— **指错了补数据的方向**。
   我 09-28 就因此错过一次：拿全阶段样本去测它，
   得到一个 **8.8% 的无意义数字**（测的不是约束对象）。
2. **`parent` 阶段整块没测过，且 case 集里也没有。**
   它的 prompt 与 `married` **不同**（6324 字 vs 7222 字），但**一次都没跑过**。

⇒ ⭐ **这一类比 ①② 更根本**：抽取再全，**没有样本也验不了**。

### ✅ 好消息：补 case 比预想容易得多

`_RELATIONSHIP_STAGES` **已经包含全部 7 个阶段**（含 stranger / parent），
`_case_friendship_hearts` 也**已有** stranger=0 / parent=10 的默认映射。

⇒ **不需要改任何逻辑，只需往 `_BASE_CASES` 里加条目。**
⇒ ⚠ `parent` 的 case **仍应给 `childrenCount`**：
case 的 `relationship_stage` 本身足以让 policy 生效（**已实测**），
但 prompt 内部会**从 `game_state` 再推导一次**阶段
⇒ 缺 `childrenCount` 会让**声明的阶段与推导出的阶段不一致**，测的就不是 parent 分支了。

⇒ ⭐ **实测顺带得到**：七个阶段的 `responseShape` **去重后只有 6 组**
（**`dating` 与 `married` 完全相同**），
而 `stranger` 的最严（「尽量用**一句**短答」）。
**别假定「阶段不同 ⇒ policy 一定不同」。**

⇒ 具体方案（含可粘贴代码）见 `docs/draft-scenarios-stranger-parent-2026-09-28.md`。
⇒ 工具：`scripts/probe_untestable_scope.py`（零请求，**同时打印两列**）。

### ④ 验证工具自身失效（本轮新发现）

**四个探针连续工作数小时、输出看起来完全正常，但「阶段」维度从头到尾是假的** ——
7 个阶段实际跑的是**同一个 prompt**。

**根因**：`ContextBuilder.build(self, npc_id, source_mods=(), morning_scenario=None, **values)`
⇒ 参数名本该是 **`friendshipHearts`**，我传的是 `relationship=stage`
⇒ **`**values` 把它吞了：不报错、不警告。**

⇒ 后果：所有「阶段 N/7」的数字都是**同一个阶段重复 N 次**。
⇒ **已修正 4 个脚本并全部重跑**；核心结论（字数 1 张卡 / 句数 6 张卡）**不变**
（因为卡名不随阶段变），但若干细节数字已更新（详见 `docs/active-work.md` 续三十）。

⇒ 应对：`probe_length_directives.py` 现在**每次运行都打印 7 个阶段的 prompt 指纹**，
若不是 7 种不同就**明示「下面所有阶段数字都不可信」**。

### ⑤ 阶段对了、话题不对（**本轮最后一层，也最容易被漏掉**）

第 ③ 类解决「该阶段有没有样本」。但**有样本 ≠ 测得到那条约束** ——
还要问：**样本问的是那件事吗？**

**实测（`probe_topic_alignment.py`）**：

```
acquaintance × 邀约    2 条约束    12 个 case    0 个匹配   ❌
     「初识阶段不得反问、邀约或主动换题；」
     「初识阶段只起一句眼前的小事，不反问也不邀约；」
acquaintance × 反问    2 条约束    12 个 case    0 个匹配   ❌
close × 动作           4 条约束    20 个 case    0 个匹配   ❌
     「亲密信号只能嵌在同一话题并最多一个当前动作；」
     「最多一个自然的亲密动作，保持角色语气；」
close × 换题 / 反问     各 1 条     20 个 case    0 个匹配   ❌
```

⇒ **acquaintance 有 12 个 case，但全是 `*-daily` / `*-coop` / `*-training` / `*-ranch`，
一个邀约场景都没有。**
⇒ ⚠ **所以「跑全 acquaintance 就能验证那条初识约束」是错的** ——
**阶段对了、话题不对，照样测不到。**
⇒ 而且**更根本的是**：那条约束**根本不在 acquaintance 生效，它在 `stranger`**
（「初识」= `stranger`，实测确认）⇒ **acquaintance 连阶段都不对**。（我先前正是这么说的，现已更正。）

⇒ 应对：`scripts/probe_topic_alignment.py`（零请求）。
⇒ **补 case 时必须按（阶段 × 话题）配对，而不是只补阶段。**

⚠ **这一类是我自己写探针时被自己的输出抓出来的**：
v1 把「长度」当成话题意图（长度是**形式属性**，没有话题词表 ⇒ 匹配恒为 0），
又没过滤**被切碎的嵌入式 JSON**（`close × 亲密` 报出 **72 条约束** —— 不可能）。
两个缺陷都会产出**看起来很像结论的假数字**，**又是第 ④ 类的形状**。

### ⑥ 写进数据、但**到不了 prompt**（09-28 深夜新增，**最容易被忽略**）

前五类都在问「**我能查到吗**」（抽取、结构、样本、工具、话题）。
第六类问的是更前一层的、**根本不属于台账职责**的事：

> **角色数据里写的规则，真的进到 prompt 里了吗？**

**实测（`scripts/probe_response_rules_reach.py`）**：

```
vanilla.json 的每个角色：写了 4 条 responseRules → 进 prompt 只有 2 条
                       ⇒ 到达率 50%
```

**根因**（`prompts.py ≈L5057`）：

```python
voice_actions.extend(sentence_pattern)                        # signatureMoves 为空时占 2 槽
voice_actions.extend(_compact_text_list(responseRules, limit=2))
voice_actions = voice_actions[:3]                             # 只剩 1 个位置
```

⇒ **「日常近况按日常说」「玩家追问后再展开研究」「不把猜测说成结论」
这几条在数据里写着，但 prompt 从来没见过它们。**

⚠ **这一层为什么危险**：台账（`constraint_scope.CURRENT`）**只扫 prompt 文本**，
所以它**看不见这个问题** —— 那些规则本来就没进 prompt，
台账既不会报缺失、也不会报冲突，**一切显示正常**。

⇒ 对「**字数话语权只有 1/6**」是**又一条独立佐证**：
**卡层 1/6 × 数据层 50% ⇒ 实际话语权比 1/6 更低。**

⚠ **诚实边界**：本次只对 `vanilla.json` 的角色取到了可靠数字；
`sve.json` / `female-bachelors.json` 存**汉化名**而 prompt 用英文名，
名字对不上 ⇒ 那部分**未计入**（见 `probe_response_rules_reach.py` 的已知缺陷说明）。

## ⭐ 这一节最该记住的一句

**一个从不失败的检查，等于没有检查。**

第 ④ 类是被**输出内容的自相矛盾**抓住的（married 阶段的卡里写着 `stage: stranger`），
不是被任何断言抓住的 —— 因为这些探针全是 `return 0` 的只读脚本。
⇒ **审计工具本身也需要被审计**，而唯一的抓手是
**「不同输入应产生不同输出」这类不变量**。

第 ⑤ 类是被**数字自己打架**抓住的（artifact 里 married 跑过 **59** 个，
而 `DEFAULT_CASES` 只有 **47** 个 ⇒ **跑过的比可跑的还多**）。
⇒ **任何计数出现「子集比全集大」，先怀疑源头，再怀疑数据。**
