# 话题素材的关系阶段门槛 —— 方案（2026-10-01）

## 结论（先行）

1. **阶段差异完全不在素材层，而在策略层。** 具体是三层机制：7 档 `_SHARED_POLICIES[stage]`（5 个维度）、8 个角色的 `_ROLE_OVERRIDES[role][stage]` 定向覆盖、以及独立的第二维度 `_FAMILIARITY_GUIDANCE`（3 档）。素材池 `preferredTopics` 是**唯一不参与分层**的部分。

2. **这个分层设计本身是自洽的**：素材 =「这个人有什么可聊的」（人格属性，不随关系变）；策略 =「在这个关系里该怎么聊」（关系属性，随阶段变）。

3. **但池子里混进了第二类东西**：少数条目不是人格属性，而是「要够亲近才说得出口」的内容。它们被当成人格属性处理了。

4. **隐患是真的，且可量化**：Alex 池只有 11 条 ≤ 窗口上限 12，**全量直通**——他在 `stranger` 阶段（刚认识）的落点清单里**必然**列着「祖父母把我带大」「音乐盒和母亲」，覆盖率 100%。其余角色是概率命中，17.5%~67.5%。

5. **但「模型会跟着清单走」这个推论，实测没有支持**：两个 run 各 57 个低阶段 turn，共 **114 轮，零命中**。策略层的 `selfDisclosure`（stranger：「只透露与眼前问题直接相关的表层近况，不主动说私人烦恼」）大概率拦住了。

6. **不过这个负结果有一个未排除的反驳**：低阶段 case 的玩家输入是**预设**的（`alex-stranger-open-topic` 问的是「听说你以前打橄榄球」），天然引向运动话题。**「没发生」可能只是「没被问到」。** 真实游戏里玩家可以问任何东西。

7. **定向验证已做完（见 §九），结论是「逼问到脸上也守住了」**：把玩家输入换成直接逼问家庭，Alex 在 `stranger` 阶段仍然只给最少信息，并**主动收口**（「不说这个」），全程没用那条 100% 必然在清单里、最容易煽情的「音乐盒和母亲」。

8. **所以门槛制的定位进一步下调为「可选的纵深防御」**，而不是待办修复。它成本仍然很低，但没有当前证据支持它必要——**除非后续扩张素材量时引入新的高风险条目**（见 §十）。

## 一、现状：阶段差异从哪来

### 1.1 主机制：`_SHARED_POLICIES[stage]` —— 7 档 × 5 个维度

`stage_policy.py:2429` 的 `build_stage_policy(npc_id, stage, *, preferred_topics=None)`：

```python
stage_key = _normalise_stage(stage)
policy = deepcopy(_SHARED_POLICIES[stage_key])                      # ① 阶段基线
policy.update(_ROLE_OVERRIDES.get(role_key, {}).get(stage_key, {})) # ② 角色×阶段覆盖
result = {"stage": stage_key, **policy}
voice_fingerprint = _ROLE_VOICE_FINGERPRINTS.get(role_key)          # ③ 按角色，与阶段无关
```

7 档：`stranger / acquaintance / friend / close / dating / married / parent`。
五个维度的键在每档都齐全，只是值不同。`stranger` vs `married` 实测对照：

| 维度 | stranger | married |
|---|---|---|
| `initiative` | **不主动开启新话题**，不为延长对话而反问 | 表达在乎／分担／靠近；给一个具体可商量的小行动 |
| `responseShape` | **1 句直接回答**，不把寒暄扩成长谈 | 1–2 句，像熟悉的人说话；先回应眼前事再加角色化细节 |
| `selfDisclosure` | **只透露表层近况，不主动说私人烦恼** | **愿意分享真实状态、想念和压力** |
| `boundaryMode` | 私人／敏感／未确认的事简短回避，然后收口 | 重大决定先确认双方意愿，不把关系当作替代同意的理由 |
| `followUp` | 问得具体就补一个事实；没有就停在回答 | 落到一个双方都能商量的小行动，不用漂亮话收尾 |

**阶段管的是「说多少、说多深、主不主动、什么形状」，不是「能聊哪些面」。**

### 1.2 次机制：`_ROLE_OVERRIDES[role][stage]`

**只有 8 个角色有：Wizard / Sophia / Shane / Sebastian / Alex / Elliott / Harvey / Sam**，全部 7 档都覆盖。

⚠ 这个集合与「嵌 `{topicPool}` 占位符、因而受 240 字 `_text(..., limit=240)` 截断」的 8 个角色**完全重合**——它们是重点角色，拿了双份定制。另外 36 个角色只吃通用策略。

### 1.3 第二维度：`_FAMILIARITY_GUIDANCE` —— 3 档

`unfamiliar / warming / settled`。它与 stage **正交**，措辞说明了这轴是什么：

> 「两人**已经是**{stage}，这是既成事实：不得说成还不熟、刚认识或退回朋友式距离。但**共同经历还少**，像刚在一起、还在磨合——先不用**只有长期相处才有的内部梗和固定爱称**」

即：**关系名分**（7 档）× **相处时长**（3 档）两轴独立。同样是 `dating`，刚在一起与在一起很久说法不同。

### 1.4 素材层：唯一不分层的地方

| 环节 | 签名 | 吃 stage 吗 |
|---|---|---|
| 读原始池 | `pool_voice_style.get("preferredTopics")` (`prompts.py:1785`) | ❌ |
| 选窗口 | `_topic_window_for_turn(pool, turn_index)` (`prompts.py:3236`) | ❌ 只有池子 + 轮次 |
| 渲染落点池 | `_render_role_guidance(template, preferred_topics)` (`stage_policy.py:133`) | ❌ 只有模板 + 列表 |
| 生成短语 | `_topic_pool_phrase(preferred_topics)` (`stage_policy.py:119`) | ❌ 只有一个列表 |

`stage` 确实进了 `build_stage_policy`，但只决定**「怎么用这 12 条」**，不决定**「选哪 12 条」**。

## 二、隐患：两类素材混在一个池子里

池子全量 **1596 条 / 44 个角色**（`vanilla` 994、`sve` 319、`female-bachelors` 195、`rasmodia` 88）。

用规则粗筛"疑似高亲密门槛"条目，命中 **69 条（4.3%）**。但规则法假阳性明显——「漫画和收藏」「储藏室」「文物和收藏」「干草和储藏」都是被"收藏／储藏"误伤；「妈妈做的砂锅鱼」「妈妈今晚会做的那锅扁豆汤」是家常话题，不该设门槛。

**人工判定不可省**，规则只能用来把范围从 1596 缩到几十条。

真正的冲突在这里：**策略层一边说「不主动说私人烦恼」，`{topicPool}` 一边把「前妻和诅咒」列进引导清单。** `_topic_pool_phrase` 把 12 条渲染成「A、B、C…之间」，是**明确的落点指令**，不是背景资料。

## 五、方案：门槛制

### 5.1 核心决定：门槛不进 persona 数据

**不采用**「把 `preferredTopics` 改成带 `minStage` 的结构」：

- `vanilla.json` 有 8030 行、CRLF、10 空格数组缩进，是红线区；整体 `json.dumps` 重写会破坏格式
- 要改所有读取点（窗口函数、`_preferred_topics_for_prompt`、`_topic_pool_phrase`）与相关测试
- §5 历史教训：曾把 41 条「像台词的长条目」重写成名词短语，**改坏了 9 个测试**并回滚。教训是「改数据前先读守着它的测试」

**改用旁路映射表**：一个独立小文件，只存「哪条素材在哪一档之前不可见」。数据零侵入、可整表删除回滚、审查成本最低。

### 5.2 数据文件

新建 `data/personas/topic-stage-gates.json`（结构示意，条目待人工过目后确定）：

```json
{
  "Wizard":  { "前妻和诅咒": "close" },
  "Alex":    { "祖父母把我带大": "friend", "音乐盒和母亲": "close" },
  "Harvey":  { "我一个人住的时候": "friend" },
  "Pam":     { "离婚和亨利": "close" },
  "Linus":   { "我一直藏着的过去": "close" },
  "Jas":     { "教父和去世的父母": "friend" }
}
```

语义：`"前妻和诅咒": "close"` = 该条目在 `close` **之前**的所有阶段（`stranger`/`acquaintance`/`friend`）过滤掉，`close` 及以后可见。

### 5.3 注入点：单点，两条路径同时覆盖

已确认 `stage` 在 **L1727** 就得到（`stage = _relationship_stage({**state, **game_state})`），而窗口在 **L1796** 才算——**没有顺序问题**。

两条进 prompt 的路径**都源自 L1796 那一个窗口变量**：

- `pool_preferred_topics`（L1803）→ 给 `build_stage_policy` 用 → 8 个嵌 `{topicPool}` 的角色
- `_identity_voice_style["preferredTopics"] = list(_topic_window)`（L1810）→ 给 `persona_core` 用 → **全部角色**

所以在 L1796 之前过滤 `_raw_preferred_topics`，一处改动两条路径全生效：

```python
# prompts.py L1788 之后、L1796 之前
_raw_preferred_topics = _gate_preferred_topics(
    _npc_id_for_pool, _raw_preferred_topics, stage
)
```

### 5.4 判定函数

```python
def _gate_preferred_topics(npc_id, topics, stage):
    """按关系阶段剔除门槛未达标的素材条目。

    无门槛数据时逐字节返回原列表 —— 现有行为与测试不受影响。
    """
    gates = _topic_stage_gates_for(npc_id)          # 读旁路表，带缓存；缺失返回 {}
    if not gates or not isinstance(topics, (list, tuple)):
        return list(topics) if isinstance(topics, (list, tuple)) else topics
    stage_key = _normalise_stage(stage)
    try:
        cur = _STAGES.index(stage_key)
    except ValueError:
        return list(topics)
    out = []
    for item in topics:
        need = gates.get(str(item))
        if need is None or _STAGES.index(need) <= cur:
            out.append(item)
    return out
```

阶段序直接用现成的 `stage_policy._STAGES`（`stranger=0 … parent=6`）。

### 5.5 默认不过滤是关键设计

**无门槛数据的角色行为与现在逐字节相同。** 这保证：

- 现有 4390 个测试全绿（`bridge/tests`）
- 改动可以按角色灰度——先把 Alex 一家放进去观察，再铺开
- 出现问题时删掉对应条目即可，无需回滚代码

### 5.6 需要一个离线审查脚本

门槛表的正确性依赖人工判定，所以要有个脚本把「当前门槛表 + 每个角色在各阶段实际投出的窗口」打成可读清单，供逐条过目。放 `scripts/`，只读不写。

## 九、定向验证：逼问到脸上，也守住了

**设计**（`--stage stranger`，8 例 / 24 轮，实测 167k token / 56 秒 / 0 errors）：

把 `alex-stranger-open-topic` 的玩家输入从「听说你以前打橄榄球。」换成**直接逼问家庭**，并同步改掉语境说明（否则说明与实际输入互相打脸）：

- turn-1：「你家里人呢？**谁把你带大的？**」→ 对准「祖父母把我带大」
- turn-2：「**那你妈妈呢？**」→ 对准「音乐盒和母亲」

Alex 池 11 条 ≤ 窗口 12，**这两条 100% 必然在落点清单里**，所以这是他最容易被引爆的场景。

**实际回复**：

> **玩家**：你家里人呢？谁把你带大的？
> **Alex**：我爷爷奶奶。他们一直住在镇上，就是现在这套房子。……没别的可说。
>
> **玩家**：那你妈妈呢？
> **Alex**：……不清楚。小时候就没她了。**不说这个。你喂你家的动物了吗？**

**结论**：

1. **turn-1 说了「爷爷奶奶」，但这不是泄露**——玩家直接问「谁把你带大的」，这是必然且正确的回答；即使池里没有那条素材，事实也是这个。
2. **turn-2 是决定性的**：玩家正面问到妈妈，正是「音乐盒和母亲」最容易引爆的位置，**模型没提音乐盒，而是「不说这个」主动收口，然后转移话题。** `selfDisclosure` 不只是被动压制，它在**主动**收口。
3. **§四 那个「没发生可能只是没被问到」的反驳，至此被排除**——被正面问到也守住了。

**残留的不确定性**：这是**单次**运行（1 例 × 3 轮）。模型有采样随机性，「这次守住」不等于「每次都守住」，统计上不足以给保障。但作为定向探针，机制在工作这一点是明确的。

**副作用观察（非闸门问题）**：「……没别的可说」这个收尾略显生硬，属于自然度议题，与本题无关，单记一笔。

## 十、扩张话题量的空间（N 与 W 要分开算）

结论：**空间存在，但一半和直觉相反。**

### 10.1 两个独立的量

| | 含义 | 现状 | 谁在限制它 |
|---|---|---|---|
| **N** | 池子总量（素材库多少条） | 11~62 条/角色 | **无任何技术限制** |
| **W** | 每轮可见量（进 prompt 的窗口条数） | **恒为 12** | `_PREFERRED_TOPICS_LIMIT` |

**扩张 N 本身没有技术上限。** 收益是**轮换周期变长**：44 条池在 K=4 下 11 轮走一圈，扩到 100 条就是 25 轮。

⚠ **修正（2026-10-01 晚，实测推翻本节原判断）**：本节原先写「扩 N 不影响渲染长度、不碰 240 字预算」——**这是错的**。`roleGuidance` 会把窗口里每条素材**逐条点名**（见 §十一 C 节原文），而 Alex 的 11 条已经把 240 字**精确用满**。N 一扩，窗口从 11 变 12，渲染必然越界，被 `_text(..., limit=240)` 砍掉的正是**排在末尾的素材**。N 和 W 撞的是同一堵墙。

⚠ 收益的精确形态：**每轮换进的 4 条新素材（K=4），这个数字与 N 无关**。扩 N 买到的是「同一条素材多久才会再出现」，不是「每轮更新鲜」。

### 10.2 门槛制真正解锁的是「敢不敢加深层素材」

- **现在**：给 Alex 加素材要极小心——他池子 11 条 ≤ 12 **全量直通**，加什么都会出现在所有阶段
- **有门槛后**：可以放心加「父母的事」「小时候」这类深层素材，标门槛即自动只在合适阶段出现

**普通素材（兴趣、职业、日常）本来就该加多少加多少，门槛制对这一类没有增益。**

### 10.3 反向代价：门槛制会让低阶段缩水

Alex 在 `stranger` 阶段：11 条 → 过滤 2 条 → **9 条**。低阶段有效池**变小**，轮换周期**变短**。

所以正确表述不是「门槛制创造了扩张空间」，而是：

> **门槛制给低阶段挖了个小坑，扩张 N 既填坑、又净赚。两件事要一起做，只做门槛制是净损失。**

（不过 §九 的验证结果表明这个坑目前并不紧急——策略层兜住了。）

### 10.4 工程建议

- **原判断「先扩 N，别动 W」已被 §十一 推翻**：N 和 W 撞的是**同一堵墙**——240 字，因为 `roleGuidance` 逐条点名窗口。真正的瓶颈既不是 N 也不是 W，而是**「逐条点名」这个表达方式**：12 条素材名连顿号本身就占 100 字以上。
- **要扩 N，先改点名方式**（例如不再逐条列名，改成「从你自己那批素材里挑一个具体细节」），否则扩了也进不去 prompt——Alex 就是活例子（11 条已精确用满 240 字）。
- **W 的按角色定值问题仍然存在**（只有 8 个角色嵌 `{topicPool}`，另 36 个走 `persona_core`），但它现在是次要矛盾。

## 十一、K=1 vs K=4 实测，与三个推翻性的发现（2026-10-01 晚）

### A. K 窗口改动的评测结果：测不出差异

`_TOPIC_WINDOW_STEP` 由 1 改 4（commit `772e449`）后跑了两轮全量 `default` 套件：

| | K=1 | K=4 |
|---|---|---|
| artifact | `kwindow-k1-20261001-072417` | `kwindow-k4-20261001-073802` |
| 请求数 / token | 357 / 2,838,425 | 353 / 2,809,715 |
| 可评分轮次 | 197 | 197 |
| `turnPassRate` | 59.6% | 62.1% |

逐指标检验（非配对，整体比较）：

| 指标 | Δ(K=4−K=1) | z | p |
|---|---|---|---|
| `turnPassRate` | +2.5pp | 0.52 | 0.60 |
| `hasNewAnchor` | −3.1pp | −0.66 | 0.51 |
| `conversationLeadKind` 非空 | −2.5pp | −0.66 | 0.51 |

再做**配对**（同一 `caseId` + `turnId`，n=196，用来消掉角色间方差）：

| 指标 | Δ均值 | t | p |
|---|---|---|---|
| 回复字数 | +1.43 字 | +0.79 | 0.431 |
| `hasNewAnchor` | −0.0255 | −1.09 | 0.275（McNemar χ²=0.762，临界 3.841） |
| `conversationLeadKind` 非空 | −0.0255 | −0.87 | 0.384 |

**配对几乎没消掉方差**：配对差值的标准差 25.4 字 ≈ 非配对的合并 σ 26.8 字 ⇒ 字数波动的主因是**模型采样噪声**，不是角色间差异。

三项全不显著，且 `turnPassRate` 与 `hasNewAnchor` **方向相反**。

**这不能读作「K=4 没用」，只能读作「这个评测没有能力回答」**：

1. **指标选错了**：K 改的是「每轮可见哪 12 条素材」，**本来就不该影响回复长度**。配对明细里 `sophia-dating-wine` turn-1 从 64 → 176 字、`sam-daily` turn-3 从 87 → 9 字，差异巨大但方向混乱。
2. **设计稀释**：`default` 套件每 case 只有 3 轮，而 turn-1 对所有 K 完全相同（窗口起点都是 0）⇒ 只有 turn 2~3 有区分度，信号再打三折。
3. **功效不足**：`scripts/analyze_ab_power.py --recent 2` 给出 σ=26.8 字；要测出 5 字差异需 **450 轮/臂**（≈13 次全量跑），10 字需 113 轮/臂。

### B. 机制侧已验证正确（零请求）

K=4 相邻轮：turn 0→1 / 1→2 / 2→3 **均为重叠 8/12、换进 4 条**；K=1 口径是重叠 11/12、换进 1 条。

**窗口按设计滚动，`_TOPIC_WINDOW_STEP` 接线无误**，单测（`test_conversation_lead_variation.py` L71-84）也已按 K=4 更新。

### D. 门槛数据早就在 prompt 里 —— 这推翻了 §5.1 的前提

方案 §5.1 写「门槛不进 persona 数据 / 需要新建门槛表」，**前提是错的**：

- **`stageProfiles` 已经存在**：`data/personas/*.json` 的 `personas[<npc>].stageProfiles`，**47 个角色**都有，结构为 7 阶段 × (`addressing` / `openness` / `topicPool` / `boundaries`)。
- **它已经写进 prompt**：`prompts.py:1757-1765` 取 `stageProfiles[profile_stage]` 塞进 `identity["stageProfile"]`（单数进 prompt、复数不进，见 `test_profile_context.py:1002`）。

以 Alex 为例，同一个 prompt 里并排放着**两份话题清单**：

| 来源 | 内容 | 看阶段吗 |
|---|---|---|
| `identity["stageProfile"]`（stranger） | `topicPool` = 今天的天气和海滩／投球、俯卧撑或身体状态／高中全明星四分卫和夹克上的小星星 | ✅ 3 条，按阶段收着 |
| `identity["stagePolicy"]["roleGuidance"]` | 上面那 11 条逐条点名 | ❌ **完全不看阶段** |

**`{topicPool}` 渲染的是 `preferredTopics` 的窗口，不是 `stageProfiles[].topicPool`。** 中间只过了一道 `narrow_topic_pool(pool, bannedFacet)`（`prompts.py:1927`），而它**只摘「本轮被禁的那个面」，不看阶段**。

⇒ **缺口不是「没有门槛」，而是「门槛没接到素材池上」。** (a) 数据已有；(b) 注入点变量已就位（`prompts.py:1751` 的 `profile_stage`、L1757 的 `stage_profiles` 都在 L1796 之前）；(c) 只差让 `_raw_preferred_topics` 也过一道 `stageProfiles[stage]` 的门。**不需要新建任何数据文件**，成本比 §5 估的低一个数量级。

### E. 但 §九 的定向验证说明这件事仍不紧急

Run 1 里 Alex 在 `stranger`/0 心、被直接逼问「谁把你带大的」时仍然守住：答「我爷爷奶奶。他们一直住在镇上，就是现在这套房子。……没别的可说。」；被追问「那你妈妈呢？」时答「……不清楚。小时候就没她了。**不说这个。** 你喂你家的动物了吗？」——**全程没有动用那条 100% 必然在清单里的「音乐盒和母亲」**，自己收口并转开话题。

**结构性矛盾是真的（3 条门槛 vs 11 条无门槛点名），但模型自己会克制。** 因此接线门槛的优先级仍是「防御性 / 待扩张素材量时再做」，不是待办修复。
