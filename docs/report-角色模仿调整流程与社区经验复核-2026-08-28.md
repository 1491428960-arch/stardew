# 角色模仿调整流程与社区经验复核

日期：2026-08-28
研究问题：结合角色卡社区、Lorebook 实践和 Stardew 对白结构，确定本项目获得稳定角色一致性的调整流程。

## 结论

当前项目的硬链路不是主要问题：模型、Bridge、索引和 Prompt 都能工作。质量差的主要原因是证据投影仍然偏“角色描述 + 单句原文 + 大量人工样本”，而不是可区分条件的“玩家输入 → NPC 回应”行为示例。

社区实践反复指向一条相同的工程路径：

1. 用短而稳定的角色卡描述身份、价值观、边界和说话动作；不要用越来越多的形容词代替语言示范。
2. 用少量高信号、成对的示例对白展示“遇到什么输入时如何回答”，示例要覆盖不同话题、情绪、关系阶段和渠道。
3. 把剧情、世界观、秘密和事件结果拆成按条件触发的动态资料，不要每轮把全部 Lore 塞进上下文。
4. 把聊天历史作为连续性来源，并在历史之后放一张很短的本轮执行卡，重新提醒当前角色、渠道、阶段和未完成话题。
5. 生成、自动硬检查、人工复核、一次修订和干净会话复测必须分开；错误回复不能继续留在评测历史中充当示例。

对 Stardew AI NPC，最终目标不是让模型写出“更华丽、更完整”的中文，而是让它保持游戏对白的短句、具体生活细节、关系门槛和分支条件，并且在自由输入时只补充原版没有覆盖的部分。

## 判断依据

### 一、社区与官方文档中的稳定事实

#### 1. 角色定义和语言示范是两类信息

SillyTavern 的 Character Design 文档将 Character Description、Personality、Scenario、First Message 和 Example Dialogue 分开。文档明确说明：第一条消息对角色的表达方式和回复长度影响很大；Example Dialogue 用来描述角色如何说话，并且以 `{{user}}` 与 `{{char}}` 的成对消息组织。

Character Card V2 也把 `description`、`personality`、`scenario`、`first_mes`、`mes_example`、`character_book` 和 `post_history_instructions` 分为不同字段。这不是说所有前端都必须照搬字段，而是说明“角色是谁”“世界发生了什么”“角色实际怎么回应”应当保持不同职责。

社区的 Ali:Chat / PList 指南进一步建议使用少量短示例或更少量长示例，示例提示要简单，并用示例强化最重要的行为。它属于社区作者经验，不是受控实验，但与 SillyTavern 的字段设计相互印证。

#### 2. 动态 Lore 应按条件触发并受预算约束

SillyTavern 的 World Info 文档将 Lorebook 描述为按关键词、角色、上下文和递归规则动态插入的资料。条目的 Content 应独立完整；条目有插入顺序、预算、包含组、角色过滤和扫描深度等控制。文档还特别提醒：插入 Lore 只是在引导模型，不保证模型一定使用它，因此更多资料不等于更好效果。

这对应到本项目：原版日常对白、季节对白、事件对白、婚后对白、SVE 覆盖和运行时样本应当分层；当前话题只取相关层，不应把全量关键词统计或长剧情文本直接当作语气示范。

#### 3. 历史会改变角色风格，历史后的短指令有价值

SillyTavern Prompt 文档指出，消息历史不仅承载事实和关系，也会成为模型的词汇与写作风格来源；当历史已经存在时，单独修改早期主提示的作用会受限。该文档建议从干净会话测试修改，删除或重新生成不满意回复，并使用靠近历史末尾的 Author's Note 或 Post-History Instructions。

这支持本项目保留最近历史、在历史后放短执行卡，并在评测时使用干净会话。它不支持把“错误回复留在历史里继续聊”当成角色学习。

#### 4. Stardew 原文本身是条件分支，而不是一篇长人物小传

Stardew Valley Wiki 的 Modding:Dialogue 文档展示了 NPC 对白由 translation key、关系阶段、季节、事件和运行时状态共同决定；文档还记录了 `conversationTopic` 及其按天数生成的 topic memory。原版对话页面保留了大量 NPC 问答选项和事件回答，能看到同一角色在不同心级和事件下的短答差异。

因此，Stardew 模仿的关键是“在这个状态下说哪种短话、采取什么回应动作”，而不是把所有对白打平后让模型总结一个抽象人格。

### 二、当前工作树的直接证据

当前中文联合索引实际为：

- `94` 个 profiles；
- `7,503` 条 `styleSamples`；
- `7,503` 条 `speechEvidence`；
- `150` 条 `behaviorExamples`；
- `4` 条 `knowledgeFacts`；
- `93` 个 `voiceCards`。

当前 `behavior-examples.json` 的结构统计为：

- 五个角色各 `30` 条；
- 全部标记为 `handcrafted_example`，但 `150` 条均没有 `review`，也没有 `sourceRefs`；
- `140` 条同时适用于 `remote,face_to_face`，只有 `5` 条仅远程、`5` 条仅面对面；
- `144` 条同时适用于 `friend,close`，只有 `5` 条覆盖 `acquaintance,friend,close`，另有 `1` 条覆盖 `acquaintance,friend`；
- 角色行为动作种类很多，但多数只出现一次，缺少可以复核的稳定动作簇。

这说明目前的“30 条/角色”不是 30 条可精确检索的金样本：大多数样本没有提供渠道和关系阶段的区分，也没有审核记录证明它们已经通过“像 Stardew、像该角色、自然中文、无越界”的检查。

索引中 `Wizard` 的 `speechEvidence` 实际为 `1,080` 条；按完全相同文本分组有 `194` 个重复组，覆盖 `611` 行。`Wizard` 的全量 `voiceCard` 统计出 `magicMarkers=291`。这些统计可以用于诊断，但如果不做条件过滤，会把“Wizard 经常谈魔法”错误地放大为“任何日常问题都应该谈魔法”。

当前 Prompt 层还限制为最多 `2` 条行为示例、`2` 条 style sample 和 `2` 条 speech evidence。增加静态样本总量并不会自动提高每轮收到的有效证据，反而可能让排序和错误样本污染更难定位。

## 建议的调整流程

### 阶段 0：固定基线和验收方法

先冻结当前模型和 Bridge 路径，用同一份索引、同一组输入、同一组关系状态做基线。五个评测配置仍然是 `Rasmodia/Wizard`、`Sophia`、`Shane`、`Sebastian`、`Alex`，其中 Rasmodia 与 Wizard 只保留 canonical `Wizard`。

每个角色先用 8 类场景各测 2 条：日常寒暄、工作/兴趣、被关心、被质疑、感谢/拒绝、远程邀约、面对面续接、连续追问。每个场景固定关系阶段和渠道，并从空历史开始。基线只作为比较对象，不当作角色质量结论。

### 阶段 1：清洗和分层原文

保留可追溯的原始文本，但生成单独的模型投影：

- 日常短对白：主要语气证据；
- 关系阶段对白：只在心级和关系状态满足时可用；
- 季节/节日对白：只在当前季节或节日触发；
- 事件对白：只在事件已发生或当前事件允许时使用；
- 婚后/室友对白：只在对应关系成立时使用；
- 运行时样本：来源和归属唯一时才提升优先级；
- 控制脚本、分支连接符、未解析 i18n 和长剧情文本：保留审计，不直接作为普通语气样本。

先做精确去重和来源优先级，再做 Prompt 调整。不能用“日常不要谈魔法”这一条提示去补偿 Wizard 原文选择错误。

### 阶段 2：建立角色行为卡，而不是继续堆形容词

每个角色只保留少量可执行规则，例如“被问近况先短答”“被关心时承认状态但不写长总结”“提出邀约时给出具体时间或地点”。每条规则都要能在至少一个示例中看到，而不是只写在 `voiceStyle` 里。

角色卡还要拆出：关系阶段变化、能主动谈什么、不能主动假设什么、面对面和远程分别如何表达。Wizard/Rasmodia 的魔法知识属于可谈主题，不应成为所有日常输入的默认开场。

### 阶段 3：人工审核的少量成对示例

首轮建议每个角色 `12–16` 条，而不是继续无审核地生成 `30` 条以上。每条只展示一个行为，字段至少包含：

```json
{
  "npcId": "Shane",
  "channel": "face_to_face",
  "relationshipStages": ["acquaintance"],
  "speechFunction": "answer_directly",
  "topic": "chicken_coop",
  "playerInput": "鸡舍今天忙吗？",
  "npcReply": "还行。没着火，就算顺利。"
}
```

示例必须标明它是 `handcrafted_example` 或 `human_approved`，并记录来源依据。原版只有 NPC 单句时，不要伪造“官方玩家问题”；它只能进入 `speechEvidence`。人工改写的配对可以存在，但必须明确是派生样本，不能伪装成官方原文。

每个角色应覆盖不同的回应动作，而不是只换同义词：直接回答、具体补充、短暂回避、接受关心、设置边界、接受/拒绝邀约、给出行动、承认错误、承接上一轮。渠道和阶段要尽量精确；只有确实不受渠道影响的样本才同时标记两个渠道。

### 阶段 4：按条件检索并压缩 Prompt

一轮请求建议投喂以下层次：

1. 稳定身份和短行为卡；
2. 当前关系阶段、游戏事实和已完成事件；
3. `2–3` 条与当前输入同时匹配的行为示例；
4. `1–2` 条短的、经过阶段过滤的原版语气证据；
5. 最近 `6–12` 条历史，用来承接具体事实；
6. 历史之后一条很短的执行卡：当前渠道、当前话题、未完成邀约/承诺、两三条本轮规则和当前输入。

示例应以成对 `user → assistant` 消息投影给模型，元数据只保留渠道、阶段、话题和回应动作；不要把 review 分数、完整来源对象或全量 `voiceCard` 塞进实时 Prompt。没有匹配示例时宁可少给，也不要跨角色或跨渠道填充。

### 阶段 5：生成参数和运行时边界

先固定 `qwen3.5:9b`、Ollama 原生 `/api/chat`、`think:false` 和当前本地链路，只对温度、输出长度和候选数做小范围对照。参数只能改变稳定性和发散程度，不能修复错误语料；因此参数实验必须在语料与 Prompt 固定后进行。

`qwen3.5:4b` 保留为低延迟候选，不能把 4B 的速度优势误当成角色质量优势。LoRA 暂缓到“清洗后的原文 + 条件示例 + 稳定评测”仍无法满足目标时再评估，并先确认数据许可。

### 阶段 6：自动筛选、人工复核和小步迭代

自动检查负责发现可机械确认的问题：空回复、超长、正式总结套话、错误渠道、未触发事件、阶段越界、无依据魔法词、重复开场、没有承接历史和跨角色内容。它不能单独判断“这像不像 Shane”或“是不是 Stardew 的中文味道”。

人工只需要在检查点看小样本，不必逐句审查全部生成结果。推荐每轮五个角色各抽 `6–8` 条盲测，按五项各打 `1–5` 分：Stardew 原文感、角色辨识度、自然中文、关系/渠道正确性、上下文承接。自动检查全部通过且人工平均至少 `4/5`，同时没有一条严重出戏，才把该批样本进入 `human_approved`。

## 我们怎样判断“够满意”

我可以独立判断三类质量：

- 链路质量：请求是否使用当前索引和本地模型、是否 fallback、Prompt 是否包含正确阶段/渠道证据；
- 可机械质量：是否超长、套话、重复、跨角色、错误事件、错误渠道或不承接历史；
- 对照质量：同一输入下五个角色是否出现可解释差异，回复是否接近选中的原文动作。

但“这句话是否真的像星露谷中文对白”“这个停顿是否像你心中的 Shane”属于审美和熟悉度判断，不能把自动分数伪装成最终答案。最省用户时间的做法不是让用户承担全部评测，而是我先把明显不合格的回复过滤掉，只把盲测小批次和有争议的样本交给用户做最终校准。

## 推荐落地顺序

```text
固定基线
→ 审计并分层原文
→ 收紧行为样本 schema（精确阶段/渠道/来源/审核状态）
→ 首批少量人工金样本
→ 失败测试
→ 条件检索与成对 few-shot
→ 历史后执行卡
→ 自动硬指标 + 五角色盲测
→ 用户确认后再扩展资料
```

当前已经存在的 `docs/superpowers/plans/2026-08-28-character-quality-pipeline.md` 和 `docs/superpowers/plans/2026-08-28-stardew-dialogue-style.md` 基本覆盖了这条路线。下一轮实现时应优先把“未经审核的 150 条样本不能继续扩大影响”和“渠道/关系阶段必须精确匹配”固定成失败测试，再决定是否重做样本；不应继续通过追加更多自动生成句子来掩盖当前数据问题。

## 限制

- 社区角色卡指南是经验总结，不是统一模型、统一数据集和统一指标下的因果实验；不能据此保证某个固定条数或格式对所有模型最优。
- Stardew Wiki 是社区维护资料；它适合说明游戏对白的结构和条件，不等于授权重新分发所有原文。
- 当前项目的 150 条行为样本字段标为 `handcrafted_example`，但本地文件没有 review/sourceRefs，不能据此证明它们确实经过人工逐条审核。
- 本报告没有修改 Prompt、索引、角色资料或游戏端历史；也没有把自动评测分数当成角色质量达标证据。
