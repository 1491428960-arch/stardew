## 这一夜用到的判断方法（下次可复用）

1. **先量后改**：改任何"配置默认值/阈值"之前，先用批次或探针量出当前行为（今晚量出 `turn_count=2` 对两人场够用、三人场必漏人，才动手改）。
2. **变异验证**：新写的测试若一次就绿，就把实现改坏一次，确认测试真能变红（今晚对 `RecentMemoryFacts` 与 `memoryHighlights` 各做一次）。**绿得可疑，就先证明它会红。**
3. **覆盖率能指路，但要看穿两种假象**：① 行为由 `subprocess` 跑的 CLI 测试覆盖时，coverage 追不到（`runtime_samples.py` 的 66% 属此）；② 按"源文件 vs 同名测试文件"比对会漏掉改名覆盖的情况（`ItemInteractionModels.cs` 实际由 `ItemInteractionRulesTests.cs` 覆盖）。用覆盖率找**整段未覆盖的公开函数**最有效。
4. **诊断优先于猜测**：真机行为异常时，先想办法把**真实请求/响应**打出来（今晚加一条响应快照诊断，一次就定位到"策略被硬编码"），不要靠改参数试探。
5. **每完成一项立即写进 `docs/active-work.md`**：长时自主作业里，落盘比记住更重要。
6. **测试夹具要贴真实数据形状**：今晚两次红牌都是我自己的夹具错了（`candidateKey` 与 `sourceKey` 被写成两个命名空间、`review_json` 的 tag 语义假设），不是实现的问题——夹具写错时先怀疑夹具。
