# 社区角色模仿方法与当前项目落地方案

日期：2026-08-27
研究问题：社区角色模仿方法与当前项目落地方案

## 结论

社区里真正有效的角色模仿方案，核心不是把 `coreTraits` 和形容词写得更多，而是把以下五层组合起来：

1. **稳定角色卡**：身份、价值观、关系边界和说话习惯只描述长期不变的部分。
2. **成对示例对白**：用“玩家说什么 → 角色如何回应”展示句长、节奏、回避方式、情绪变化和具体措辞。
3. **按条件触发的动态资料**：地点、事件、关系阶段和秘密只在当前条件成立时注入。
4. **靠近生成位置的短提醒**：在历史之后再次强调本轮的语气和输出边界，避免长上下文把角色卡冲淡。
5. **干净的角色评测历史**：错误回复要删除或重开会话，否则错误语气会成为下一轮的错误示例。

对当前项目的判断是：资料索引和阶段过滤方向已经正确，但现在仍偏向“角色描述 + 原文单句 + 约束清单”，缺少高信号的成对示例和话题／言语行为标签。这可以解释为什么模型能提到角色相关名词，却仍然写成统一的书面中文：它拿到了“谈什么”的证据，却没有充分学到“面对不同输入时，角色怎样说”。

推荐的下一阶段不是继续给每个角色堆形容词，也不是立即 LoRA 微调，而是为五个评测角色建立少量、人工审核的 `playerInput → npcReply` 示例集，并把示例按话题、关系阶段、情绪和渠道检索。先在干净会话中验证，再决定是否扩展到全部 NPC。

## 判断依据

### 一、社区来源反复验证的事实

#### 1. 示例对白比性格形容词更能传达“怎么说”

SillyTavern 的角色设计文档把角色描述、性格、场景、第一条消息和 Example Dialogue 分开，并明确把第一条消息和示例对白作为展示角色表达方式的地方。示例对白不是剧情百科，而是让模型看到角色在具体输入下的回答格式、长度和语气。

Character Card V2 也把 `description`、`personality`、`scenario`、`first_mes`、`mes_example` 分成独立字段。这种结构本身说明“角色是什么”和“角色实际说什么”不是同一种信息。

社区 Ali:Chat / PList 指南进一步把成对示例作为角色卡的主要调教材料：示例需要覆盖不同话题、情绪和关系，而不是反复写同一种“你好”或把标签改写成散文。它是社区实践指南，不是受控实验，但与 SillyTavern 的字段设计一致。

**对本项目的推断**：当前 `data/personas/*.json` 中的 `voiceStyle` 适合做稳定规则，但 `openers`、`closers` 和 `tone` 不能替代成对示例。特别是“疲惫但不卖惨”“自信但会用行动回应”“克制而不主动神秘化”这类行为，必须用具体问答展示。

#### 2. 稳定人设、动态世界资料和聊天历史应分层

SillyTavern 的 World Info / Lorebook 机制以关键词或条件触发条目，并提供优先级、预算、递归、sticky 和 cooldown 等控制。它的基本思想是：不是每轮把全部世界观塞给模型，而是只在当前话题或状态相关时插入资料。

Character Card V2 还把 `character_book`、`system_prompt` 和 `post_history_instructions` 作为独立扩展点，分别承载动态知识、全局指令和历史之后的提醒。

**对本项目的推断**：`ProfileIndexStore` 已经按 NPC、来源 Mod、关系阶段和事件过滤 `speechEvidence` / `styleSamples`，这是正确的骨架；下一步应增加“话题／言语行为”过滤，而不是单纯把每个角色的原文条数从 6 条提高到 30 条。

#### 3. 上下文越长，早期角色约束越容易失效

SillyTavern 的 Prompt 文档和 Prompt Manager 文档都把消息顺序、角色卡、聊天历史、Author's Note 及历史后的指令当成可控制的上下文组成部分。社区常把短的 Author's Note、Character Note 或 Post-History Instructions 放到接近生成位置，用来重新提醒当前风格。

Nature 论文《Role play with large language models》从模型行为角度指出，角色不是一次性写入后永久固定的状态，而会在上下文中逐步形成和修正；后续对话可能改变模型当前维持的角色表现。

**对本项目的推断**：当前 PromptBuilder 已把历史限制为最近若干条，并声明“历史用于承接，不是语气来源”。这个边界需要保留；但还应在历史之后增加一条很短的“本轮角色执行卡”，只包含当前渠道、话题、关系阶段和 2～3 个最关键语气动作，避免重复注入整张 persona。

#### 4. 错误历史会把错误模仿固化

SillyTavern 的角色设计和聊天使用文档都把删除不满意回复、重新生成、从干净历史继续作为常见工作流。原因很直接：上一轮错误的回复会成为下一轮上下文的一部分，模型可能把它当成角色已经采用的表达方式。

**对本项目的推断**：五角色横向比较必须使用新会话或清理过的会话。不能用已经被统一书面腔污染的长历史，来证明某个角色“本来就不贴”。网页端保存会话是用户体验需要，但评测模式应该另有“新建评测会话”入口或明确的隔离会话 ID。

### 二、当前项目代码观察

- `bridge/src/stardew_ai_bridge/prompts.py` 已注入 `voiceStyle`、`speechEvidence`、`styleSamples`、关系阶段、故事事实和有限历史，也已经要求模型模仿原文的用词、句长和节奏。
- `bridge/src/stardew_ai_bridge/profile_index.py` 的证据选择已做 NPC、来源 Mod、关系阶段和来源优先级过滤，并特别保留来源 Mod 的证据；目前接口主要按这些维度筛选，没有看到按玩家输入话题或言语行为选择示例的独立维度。
- `bridge/src/stardew_ai_bridge/speech.py` 会从原文统计 `magicMarkers`、边界、犹疑和干燥幽默等特征，并生成 `voiceCard`。这些统计适合做检索和诊断信号，但统计词频本身不能告诉模型“玩家质疑时先嘴硬，随后用行动回应”这类交互行为。
- `data/personas/rasmodia.json` 已有 `voiceStyle`、`stageProfiles`、`knowledgeRules` 和来源引用；Wizard/Rasmodia 统一为 canonical `Wizard` 是正确的身份建模。问题不在于缺少更多同义形容词，而在于缺少“在日常寒暄、被追问、被关心、面对邀约、涉及危险话题时分别如何回答”的成对示范。
- 当前五角色实测中，Sophia、Shane、Sebastian、Alex 能偶尔提到各自主题，但这只能证明检索到了一些内容，不能证明模型已经稳定复现其语气。书面化、泛化和魔法词过多仍属于未解决的质量问题。

### 三、应当采用的角色资料格式

建议在现有稳定 persona 和原文证据之外，新增独立的“行为示例”层。示例可以来自人工编写或人工审核的原版改写，但不能伪装成游戏原文：

```json
{
  "exampleId": "shane:work:acquaintance:direct-answer-01",
  "npcId": "Shane",
  "channel": "face_to_face",
  "relationshipStages": ["acquaintance", "friend"],
  "speechFunction": "answer_directly",
  "topic": "work_pressure",
  "emotion": "tired_dry_humor",
  "playerInput": "今天工作还顺利吗？",
  "npcReply": "还行。鸡舍没着火，我就算赢了。你呢？",
  "sourceType": "handcrafted_example",
  "sourceRefs": ["vanilla:Shane:work-tone"]
}
```

这里的关键不是示例句子本身有多华丽，而是每条示例都同时回答四个问题：玩家在问什么、角色此时是什么关系和情绪、角色采取什么回应动作、这种回应用了什么语言节奏。对原版只有 NPC 单句而没有玩家输入的语料，应保存为 `speechEvidence`，不要硬造一个“官方玩家问题”；只有人工创作并审核的配对才进入 `handcrafted_example` 层。

## 证据

- 调研截止：2026-08-27。关键网页来源均记录为直接链接；Reddit、Google、Character.AI 文档和部分 arXiv 页面访问不稳定，未作为本报告的核心事实依据。
- 当前代码检查显示，`PromptBuilder` 已有独立的 `voice_card`、`speech_evidence`、`style_evidence` 和 `conversation_history` 消息层；这证明项目已经具备分层注入的实现基础，但不等于已经具备成对示例检索。
- 当前 `ProfileIndexStore.style_samples()` / `speech_evidence()` 的可见筛选维度是 NPC、来源 Mod、关系阶段和上限；玩家输入没有作为话题检索条件传入。该结论来自本地代码阅读，尚未通过新增测试固定。
- 当前 `speech.py` 的语气卡是根据原文标记词生成的特征与 `topicHints`；这是可解释的诊断层，但不是交互示例层。该结论来自本地代码阅读。
- 旧有本机评测与网页记录只能说明“部分角色主题证据进入了上下文”，不能单独证明角色语言风格稳定。完整质量判断仍需干净会话、多轮和人工复核。

## 建议

1. **最高优先级：建立五角色干净评测集**。每个角色至少覆盖日常寒暄、工作／兴趣、被关心、被质疑、感谢／拒绝、邀约和连续追问；每个场景记录输入、关系阶段、渠道和“应该出现的行为”，不只记录关键词。
2. **先做 8～12 条高质量成对示例，不做 30 条随机台词**。每个示例只承担一个清晰行为，覆盖不同情绪和关系阶段；由人工审核自然度。示例应进入独立文件或独立索引层，不能和原版事实混在一起。
3. **把检索从“角色级”推进到“角色 + 阶段 + 渠道 + 话题 + 言语行为”**。每轮取 3～5 条相关示例，另取少量原文风格证据；动态剧情资料继续按事件状态单独过滤。
4. **在历史之后加入短的本轮执行卡**。内容只保留当前渠道（远程／面对面）、关系阶段、当前话题、一个未完成邀约或承诺，以及 2～3 条角色行为规则；不要把完整 persona 再复制一遍。
5. **把远程聊天和面对面聊天建成同一条故事线的两个 channel**。线上形成的邀约、承诺和未完话题保存为结构化 `openLoop`；面对面进入时检索该条状态并继续推进，不能只依赖历史文本中的偶然一句话。
6. **增加“新建干净评测会话”和错误回复隔离**。网页持久化继续服务用户聊天，但批量比较五个角色时必须清空历史或使用独立会话；不把上一轮模型生成结果写回静态角色示例。
7. **把质量测试从“证据词命中”扩展为行为断言**：例如 Shane 被问工作时先短答并带干巴巴玩笑；Alex 被质疑后给出行动计划；Rasmodia 日常问题先直接回答且不无故引入魔法；Sebastian 避免客服式完整总结。断言应允许自然措辞变化，不能用字符串后处理强行改写输出。
8. **暂缓 LoRA 和大规模自动生成示例**。先用现有 Qwen3.5 9B/4B、同一份证据和同一套干净评测集分离“模型能力”和“上下文设计”影响；只有结构化示例仍不足时，才评估带来源、已清洗且许可明确的 LoRA 训练集。

推荐的实现顺序是：

`行为示例 schema → 失败测试 → 少量人工示例 → 话题/行为检索 → 历史后执行卡 → 干净评测 → 再扩展角色资料`。

## 限制

- 本报告总结的是角色卡和本地角色扮演社区的公开实践，不是统一模型、统一题集下的严格对照实验；“示例对白更有效”在这里是多份文档一致支持的工程结论，不宣称已完成因果实验。
- Ali:Chat / PList 指南属于社区作者经验，格式与建议可能随前端、模型和模板变化；它不能直接决定 Stardew NPC 的最终数据格式。
- Nature 论文研究的是一般角色扮演行为，不是 Stardew Valley 或中文 NPC；它支持“上下文会改变角色表现”的方向性判断，不直接给出本项目的 Prompt 模板。
- 当前报告没有修改 `PromptBuilder`、persona、索引器或 SMAPI；也没有新增测试、启动游戏或重新进行完整 Bridge 质量评测。因此不能把建议表述为已经修复角色不贴的问题。
- 当前已有的语料多数是 NPC 原版单句，不天然包含玩家输入。把它们改造成成对示例需要人工设计和审核，不能把合成问题伪装成官方证据。
