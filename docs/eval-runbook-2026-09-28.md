> **本文回答一个问题：什么时候该跑云端评测、跑多大、跑完能声称什么。**

> 5,696 万 token，而其中相当一部分批次在统计上本就无法判定。

## 一、三个实证（决定了规范为什么长这样）

| 事实 | 数值 | 含义 |
|---|---|---|
| **成本几乎全是"重发 prompt 的次数"** | 输入占 **99.6%**、输出只 **0.4%**；平均 4,972 token/请求 | 改 prompt 措辞对**成本**几乎零影响，只有**减少请求数**有效 |
| **重试是最大的可乘项** | 占请求 **20.5%**；其中 **`response_affection_retry` 占 54%**（480/897） | 一次重试 = 一次完整请求（含约 5k token 输入） |
| **小步迭代不可归因** | 单次跑 σ ≈ **24 字** > 效应 **5.7 字**；三个**未改**角色同期自己就降 10~14 字 | 12-case 单次跑只能测出 ≥ 17 字的差异；**5 字效应需约 430 轮/臂** |

⇒ **结论**：项目的验收一直是**人读样例**（`STATE.md` 多处写明"不能把自动评分当人工质量结论"）。
既然如此，用统计 A/B 的规格去跑小改动，就同时付出了统计的成本、又拿不到统计的结论。

重试画像（全 2,642 个 case，652 个发生过重试 = 24.7%）：

| 重试类型 | 次数 |
|---|---:|
| `response_affection_retry`（缺个人亲近） | **480** |
| `response_conversation_lead_retry`（缺接话点） | 183 |
| `response_format_retry`（格式噪声） | 164 |
| `response_topic_retry` | 26 |
| `response_continuity_retry` | 19 |
| `response_schedule_retry` | 18 |
| 其余（close / restatement / skipped / failed） | 7 |

复现：`node E:\workspace\.scratch\probe-retry-profile.mjs`

## 二、跑前闸门（**不通过不许跑**）

跑之前必须答完这三条，答案写进本批次目录的 `PLAN.md`：

1. **这次要回答的一个问题是什么？**（一句话，可判定）
2. **预期的效应有多大？** 用既有数据估计。
   - 若 **< 17 字**（12-case 单次跑的可检测下限）⇒ **禁止跑统计 A/B**，
     走 §三 的 **L1 人读档**（拿样例说话，不做数值声明）。
   - 若确实需要数值结论 ⇒ 先用 `python scripts/analyze_ab_power.py` 算样本量，
     达不到就**别跑**（跑了也是零信息量）。
3. **预算多少？** 按下式估，写在 `PLAN.md` 里：
   ```
   请求数 ≈ case 数 × 轮数 × (1 + 预期重试率 ~0.2)
   token  ≈ 请求数 × 5,000
   ```

> 参照：一次 L1（6 case × 3 轮）≈ **22 请求 / 11 万 token**；
> 一次 L2（12 case × 3 轮 × 2 臂）≈ **86 请求 / 43 万 token**。
> 而 09-15 单批（50 case）跑到 **279 万 token** —— 那是 25 倍于 L1 的量级。

## 三、三档跑法（先问"我要什么结论"，再选档）

| 档 | 何时用 | 规模 | 跑完能声称什么 |
|---|---|---|---|
| **L0 零请求** | 默认第一站 | 0 | 静态事实（`health_check.py` + 各 probe + 读历史 artifact） |
| **L1 人读档** | 改措辞、调风格、看"贴不贴" | 5~12 case | **"这几条样例变好了/变差了"** —— 只能陈述样例，不做统计声明 |
| **L2 统计档** | 只有需要数值结论时（如违规率下降 X%） | 按算出的样本量 | 可按数值声明，**须同时给出样本量与置信口径** |

**三条硬规则：**

1. **默认走 L1。** L2 是例外，必须先在 §二 第 2 条算出样本量。
2. **L1 的产物不写"pass 率提升了"**，只写"逐条读下来如何"。自动评分只能当**筛选器**，不能当结论。
3. **跨批次比较必须先确认口径一致**：case 集合相同、`--limit` 相同、prompt 路径相同。
   口径不同的两个批次**不可比**，别放同一张表里。

## 四、成本护栏（执行层，立即可用）

1. ⛔ **禁止用 `--max-requests` 做"省着跑"**。它会让两次跑覆盖的 case 数不同
   ⇒ 结果不可比 ⇒ 必然重跑，**重跑比一开始跑全更贵**。
   要控制规模就用 `--limit`（固定 case 数），并在记录里写明。
2. ✅ **单批 `--max-total-tokens` 保持显式设置**（现状经济模式 200,000），
   预算停止（`budgetStopReason` 非空）的批次**标记为不完整**，不参与任何对比。
3. ✅ **不跑评测时停掉 Bridge**。`BRIDGE_CLOUD_ONLY=true` ⇒ Bridge 只要活着，
   任何一次试聊都在花钱。查 `5678` 是否在监听即可确认。
4. ✅ **`node E:\workspace\hub\scripts\_cc_split.mjs` 作为常规体检**（按需、非定时）。
   它能算出差额：**官方计费 − 本地会话日志 = 影子调用**。
   2026-09-28 实测全局影子占比 **54.4%**（池 3 高达 85.6%）——
   不查这个数，就会以为额度还有很多。
5. ✅ **额度规划**：星露谷事实上独占 Command Code 池 3（全工作区唯一持有 `CMD_API_KEY_3` 者）。
   池见底 = 云端实验全线停摆，且要等周窗口重置。**开工前先看池余量**：
   `node E:\workspace\hub\scripts\_cc_pools.mjs`

## 五、待改代码（需单独立项，附验收口径）

按性价比排序。**改前先 `grep` 测试有没有钉住相关值**（`AGENTS.md` 的既有纪律）。

### 1. ⭐ 把"重试是否有效"落盘（**最高优先，零行为变更**）

`guard.py:1456` 已经算了 `_retry_quality_key(prompt, reply)` 用来在两个候选里取优，
但这个分数**没有写进 artifact** ⇒ **现在无法判断 480 次 affection 重试里有多少是白跑的**。

- 改法：把重试前后的 quality key 一并记入 `warnings`（如
  `response_affection_retry_effective: 3->5` / `..._ineffective: 5->5`）。
- 验收：跑一批 L1，artifact 里能看到每类重试的有效率。
- 价值：**这是唯一能把"重试成本"与"重试收益"对上的手段**。不落盘，后面所有重试优化都是猜。

### 2. ⭐ 收窄 `missing_proactive_affection` 的触发面（占重试 54%）

项目已做过一轮收窄（`initiativeExpectation=none/responsive` 不再触发），
但**480 次重试说明还没收干净**。

- 改法：先做 **1**，拿到有效率数据再决定收窄哪一支 —— 有效率低的那些场景直接不重试。
- 验收：重试占比下降，且**人读样例没有变差**（L1 判定）。
- ⚠ 不要用"减少重试 ⇒ 请求少了"单独作为验收 —— 必须同时给出人读样例对照。

### 3. 禁掉 `--max-requests` 的误用（或让它显式报错）

- 改法：`run_character_quality_eval.py:1591` 的 `--max-requests` 在被显式传入时，
  于 `summary.json` 里记 `truncated: true`，并在结果接口标注"本批不可跨批比较"。
- 验收：用 `--max-requests` 跑一次，summary 出现 `truncated: true`。

### 4. ✅ 跑前闸门自动化（**已落地 2026-09-28**）

- 改法：加 `--plan` 干跑模式（对齐 `design_rules_experiment.py --plan` 的既有形态），
  打印 §二 的三条答案模板与预估预算，**不发请求**。
- 验收：`--plan` 退出码 0、零请求、输出含请求数与 token 预估。✅ **已满足**
- **落地记录**：`run_character_quality_eval.py` 加 `--plan` + `_print_plan()`。
  放在 cloud dry-run **之前** —— 它对**所有** provider 都生效（它回答的是「该不该跑」，
  而不是「云端要不要确认」）。选例逻辑与 `main()` **逐字一致**，否则预估会失真。
  额外做对的两件事：① 传 `--max-requests` / `--max-total-tokens` 时**主动警告不可比**；
  ② 轮数 < 36 时警告「本批只能走 L1 人读档」。
  ⭐ 意义：把 §二 的三问变成**运行时输出**，而不是只写在文档里 ——
  文档里的规则**跑起来照样能违反**，审计里就有这样的批次。
- 实测：`--plan --suite default --limit 6` ⇒ 6 case / 18 轮 / **22 请求** / 11 万 token，
  并自动报出「18 轮 < 36 轮 ⇒ 只能走 L1」。测试 2 条，**4317 passed**。

## 六、一页速查

```
改了什么？
  ├─ 只改了 prompt 措辞 / 人设 → L0（health_check）→ L1 人读（5~12 case）
  ├─ 要一个数（如"违规率降了 X%"） → 先算样本量 → 不够就别跑
  └─ 想"再跑一批看看" → ⛔ 先答 §二 三问；答不上就是不该跑

跑之前：池余量？（_cc_pools.mjs）  Bridge 关了吗？（5678）
跑的时候：--limit 定规模，别用 --max-requests
跑之后：口径一致吗？预算停了吗？记进 active-work
```
